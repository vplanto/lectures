# Лекція Y: Методологія USE. Від "ворожіння на кавовій гущі" до системної діагностики

## ⚡ Експрес-опитування: Активація знань

Перед тим як зануритися в методологію Брендана Грегга, перевіримо, наскільки ви довіряєте своїм дашбордам.

1.  **Metric Trap:** Ви дивитесь на графік CPU в Grafana. Інтервал агрегації — 1 хвилина. Середнє значення — 60%. Чи гарантує це, що у вас немає тротлінгу або черг на CPU?
2.  **Saturation:** У вас диск (NVMe) показує 100% Utilization. Чи означає це, що latency запитів обов'язково деградувала?
3.  **Blind Spot:** Яку метрику найчастіше ігнорують інженери при аналізі `OOMKilled`, фокусуючись лише на графіку "Memory Usage"?

<details markdown="1">
<summary>Наші очікування (відповідь)</summary>

1.  **Ні.** За 1 хвилину могло статися 10 мікро-спайків (micro-bursts) до 100% тривалістю по 200 мс. Це призведе до latency spikes, які згладжуються середнім значенням. Це проблема **Resolution**.
2.  **Не обов'язково.** Якщо це бекграунд-процес (scavenger/compaction) з низьким пріоритетом, він може "їсти" всі вільні цикли, не блокуючи основні I/O. Але якщо $Saturation > 0$ (є черга) — тоді так, latency виросла.
3.  **Allocation Failures / Rate.** Пам'ять може бути вільною (Usage < Limit), але фрагментація або швидкість виділення (rate of allocation) перевищує можливості ядра звільнити сторінки (reclaim). Дивитися треба на `failcnt` або rate of allocation, а не лише на статику.

</details>

## Вступ: Проблема "Fishing Expedition"

Більшість інженерів при інцидентах діють як туристи на рибалці: закидають вудку навмання.

  * "А гляньмо CPU..."
  * "А може це мережа?"
  * "А давай рестартнемо под, може попустить."

Цей підхід називається **Anti-Method**. Він працює для простих проблем, але на High-load системах це марнування часу (MTTR росте).

Сьогодні ми розбираємо **USE Method** (Utilization, Saturation, Errors) — фреймворк, який змушує вас діяти як патологоанатом, а не як ворожка. Мета: перевірити **всі** ресурси системи за чітким алгоритмом, щоб не пропустити "невидиму" проблему.

## Три Стовпи USE

Для **кожного** ресурсу (CPU, Memory, Disk, Network Interface, Interconnects) ми маємо отримати три метрики. Якщо хоч однієї немає — ви "сліпі" в цьому секторі.

### 1\. Utilization ($U$)

Відсоток часу, коли ресурс був зайнятий роботою.
$$U = \frac{Busy\_Time}{Total\_Time}$$
*Для нечасових ресурсів (RAM, Disk Space):* $U = \frac{Used\_Capacity}{Capacity}$

### 2\. Saturation ($S$)

Міра черги. Робота, яка *не може* бути виконана зараз і чекає.

  * **Це головний предиктор Latency.**
  * Якщо $S > 0$, значить час відповіді вже деградував.
  * *Приклади:* CPU Run Queue, Disk Wait Queue, Memory Paging/Swapping.

### 3\. Errors ($E$)

Кількість помилок при зверненні до ресурсу.

  * **Правило крові:** Починати аналіз треба звідси.
  * Високий CPU може бути наслідком нескінченних ретрав через битий пакет мережі.

## Технічний розтин: Матриця Ресурсів (Linux/K8s Context)

Перетворимо теорію на конкретні метрики `node_exporter` та системні файли.

| Ресурс | Utilization ($U$) | Saturation ($S$) | Errors ($E$) |
| :--- | :--- | :--- | :--- |
| **CPU** | `/proc/stat` (user + sys) | `/proc/loadavg` (або PSI `some`), Run Queue length | ECC errors, Machine Check Exceptions |
| **Memory** | `Free` / `Total` | **Paging/Swapping** (`vmstat`), **OOM Kills** | Failed allocations (`failcnt` in cgroup) |
| **Network** | RX/TX throughput / Bandwidth | `dropped` packets, buffer overruns (`ifconfig`, `netstat`) | `collisions`, `errors`, TCP Resets |
| **Disk I/O** | `%util` (iostat) | `avgqu-sz` (Average Queue Size) | I/O Errors, S.M.A.R.T. alerts |

### Приклад "Сліпої зони"

Інженер бачить: `CPU Usage: 30%`.
Висновок інженера: "Процесор не є ботлнеком".
**Реальність (USE):**

  * $U = 30\%$
  * $S$ (Saturation) = Critical.
  * **Причина:** Один тред вперся в ліміт одного ядра (Single Thread Performance), або процес чекає на Memory Lock. Загальний CPU низький, але задача стоїть у черзі на конкретний м'ютекс або ядро.

## 🛑 Engineering Reality Check: Де метод бреше

USE — це не срібна куля.

### 1\. Проблема Sampling Rate (Nyquist–Shannon)

Prometheus скрапить метрики раз на 15-30 секунд.

  * Якщо у вас мікросервіс обробляє запит за 5 мс, а спайк навантаження триває 100 мс — Prometheus цього просто не побачить (Aliasing).
  * **Рішення:** eBPF профайлінг, який знімає події в ядрі, а не семпли.

### 2\. Utilization для I/O — це брехня

Для сучасних SSD/NVMe дисків метрика `%util` в `iostat` вводить в оману.

  * Диск може показувати 100% утилізації, але при цьому приймати ще 10x IOPS, бо всередині контролера є паралелізм.
  * **Висновок:** Для стореджа дивись тільки на **Saturation** (Queue Length) та Latency. Утилізація — це шум.

### 3\. "Відсутні" метрики

Хмарні провайдери (AWS/GCP) часто ховають рівень гіпервізора. Ви бачите віртуальний диск, але не бачите насичення фізичного каналу до стореджа (IOPS throttling на рівні EBS). Ви бачите це тільки як зростання Latency.

## Практичне завдання: Думай як Perf Lead

Дано: Kubernetes Node. Скарги на "тупіння" додатків.

  * **CPU Usage:** 70%
  * **Memory Usage:** 60%
  * **Disk I/O:** низький.

Але додатки періодично "завмирають" на 1-2 секунди. Ви підозрюєте **Memory Saturation**, хоча вільної пам'яті наче вистачає.

**Задача:** Яку *одну* специфічну команду в терміналі (або метрику) ви перевірите, щоб підтвердити діагноз "Memory Pressure" без OOM?

<details markdown="1">
<summary>Обґрунтування рішення</summary>

**Перевірити PSI (Pressure Stall Information) або `vmstat`.**

Команда: `cat /proc/pressure/memory`
Або метрика: `node_pressure_memory_stalled_seconds_total`

**Чому?**
Система може не вбивати процес (OOM), а агресивно звільняти Page Cache (file-backed pages), щоб знайти пам'ять для алокації. Це викликає **Major Page Faults**. Процесор встає на паузу, чекаючи, поки сторінка коду знову завантажиться з диска в RAM.
Usage нормальний (60%), але система перебуває в стані thrashing (постійне вивантаження/завантаження сторінок). PSI покаже ненульовий `some` або `full` stall time.

</details>

## ✅ Контрольні питання

1.  **Пріоритет:** Чому Грегг наполягає починати аналіз з **Errors**, а не з Utilization, хоча Utilization графіки "красивіші"?
2.  **Формула:** Напишіть формулу $U$ (Utilization) для ресурсу, який не вимірюється в часі (наприклад, HDD capacity).
3.  **Взаємозв'язок:** Чи може бути $U = 100\%$ і $S = 0$? Наведіть приклад.
4.  **Інструментарій:** Чим метрика `Load Average` (Linux) відрізняється від чистого CPU Utilization? Що вона враховує крім CPU?
5.  **K8s Limits:** Як USE Method застосувати до K8s Pod, який має `cpu limit = 1000m`? Що буде $S$ (Saturation), якщо под хоче 1500m? (Підказка: CFS Throttling).
