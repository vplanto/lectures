# Лекція X: Еволюція Хмари. Від "Няньки серверів" до Application-First

## Експрес-опитування

Перед тим як говорити про майбутнє, згадаємо "біль" сьогодення. Уявіть, що ви пишете мікросервіс, якому треба зберегти повідомлення в чергу (Kafka) і записати дані в базу (PostgreSQL).

1.  Скільки бібліотек (SDK) вам доведеться додати у ваш `pom.xml` / `build.gradle`?
2.  Якщо ми вирішимо замінити Kafka на AWS SQS — скільки рядків коду вам доведеться переписати?
3.  **Advanced:** Ви додали бібліотеку для `Retry` (щоб повторювати запит при помилці). Де цей код виконується: у вашому додатку чи на сервері бази даних? Хто платить CPU за ці повтори?

<details markdown="1">
<summary>Наші очікування (відповідь)</summary>

1.  Мінімум дві "важкі" бібліотеки: драйвер для PostgreSQL (JDBC) та клієнт для Kafka. Це збільшує розмір вашого JAR-файлу і споживання пам'яті (Metaspace).
2.  Багато. Логіка роботи з Kafka та SQS відрізняється. Вам доведеться переписати методи відправки повідомлень, обробку помилок та конфігурацію. Це порушує принцип **Portability**.
3.  Код виконується у **вашому додатку** (Client-side logic). Саме ваш сервіс витрачає CPU на цикли повторів, серіалізацію даних та очікування тайм-аутів.

## Вступ: Проблема "Сантехніки" в коді

Сьогодні ми розглянемо концепцію **Application-First Cloud Services**.

Але почнемо з проблеми. У сучасному **Compute-First** світі (Docker, Kubernetes) ми стали "няньками інфраструктури". Ми витрачаємо 30% часу на бізнес-логіку ("як розрахувати знижку") і 70% на "сантехніку":

  * Як підключитися до бази?
  * Як оновити секрети?
  * Як налаштувати Service Mesh?
  * Як прописати YAML-конфіги для K8s?

Ваш код перевантажений інфраструктурними залежностями. Це робить його "важким" і складним для зміни.

## Три Епохи Архітектури

Згідно з Bilgin Ibryam (співавтор *Kubernetes Patterns*), ми проходимо через три етапи:

### 1\. Pre-Cloud (Monolith)

  * **Світ:** Все в одному процесі.
  * **Відповідальність:** Розробник пише все — від бізнес-логіки до пулу з'єднань і кешування.
  * **Проблема:** Тісний зв'язок (Tight Coupling). Змінити базу даних — це переписати половину програми.

### 2\. Compute-First (Microservices + K8s) — *Де ми зараз*

  * **Світ:** Контейнери. Інфраструктура (K8s) дає нам CPU та RAM, але вона "німая".
  * **Механіка:** Ми "в'яжемо" сервіси між собою. Ops-команда пише кілометри YAML-файлів, щоб змусити Сервіс А бачити Сервіс Б.
  * **Проблема:** **Cognitive Load**. Розробник має знати все: про мережі, DNS, storage classes. Інфраструктура "протікає" в код через SDK.

### 3\. Application-First (The New Way)

  * **Світ:** Інфраструктура як API.
  * **Концепція:** Ви не підключаєте бібліотеку Kafka. Ви робите HTTP-запит на `localhost`, кажучи: *"Збережи це повідомлення в тему 'orders'"*.
  * **Інструмент:** **Dapr** (Distributed Application Runtime), **Bindings**.
  * **Результат:** Ваш код нічого не знає про інфраструктуру. Сьогодні це Kafka, завтра — RabbitMQ, післязавтра — Azure Service Bus. Код не змінюється. Змінюється лише конфігурація "Sidecar" процесу.

## Технічний розтин: Як це працює (Sidecar Pattern)

У моделі Application-First "важка робота" виноситься з вашого коду в окремий процес-помічник (Sidecar), який живе поруч з вашим додатком.

| Характеристика | Класичний підхід (SDK) | Application-First (Dapr/Sidecar) |
| :--- | :--- | :--- |
| **Комунікація** | App -> TCP -> Database | App -> HTTP/gRPC (localhost) -> Sidecar -> TCP -> Database |
| **Залежності** | Потрібен `kafka-client.jar` (10MB+) | Потрібен лише стандартний HTTP клієнт |
| **Retry / Circuit Breaker** | Реалізовано в коді (бібліотека Resilience4j) | Реалізовано в Sidecar (конфігурація YAML) |
| **Мова програмування** | Залежить від SDK (Java, Go, Python) | Будь-яка (всі вміють робити HTTP запити) |

### Приклад коду (Псевдокод)

**Було (SDK):**

```java
// Тісний зв'язок з Kafka
KafkaProducer producer = new KafkaProducer(props);
producer.send(new ProducerRecord("orders", orderData)); // Треба знати API Kafka
```

**Стало (Application-First):**

```java
// Ніякої Kafka. Просто HTTP.
httpClient.post("http://localhost:3500/v1.0/publish/orders", orderData);
```

## Engineering Reality Check: Ціна абстракції

Як інженери, ми знаємо: **безкоштовних абстракцій не існує**. Якщо стаття на InfoQ продає вам "ідеальний світ", ваше завдання — знайти підступ.

Аналізуємо ризики:

### 1\. Податок на затримку (The Latency Tax)

Кожен запит тепер робить додатковий стрибок (hop).

  * *Раніше:* Прямий сокет до бази (0.5 ms).
  * *Тепер:* Серіалізація JSON -> HTTP call -> Sidecar -> Десеріалізація -> Логіка -> Виклик бази.
  * **Висновок:** Для High-load систем (де боротьба йде за мілісекунди P99) цей оверхед може бути неприпустимим.

### 2\. Пекло налагодження (Black Box Debugging)

Коли ви отримуєте помилку `500 Internal Server Error` від Sidecar-а:

  * Stack Trace у вашій Java-програмі чистий. Ви просто отримали 500.
  * Помилка сталася десь у "хмарі" або в коді Sidecar-а (написаному на Go).
  * **Висновок:** Щоб знайти проблему, вам потрібен просунутий Distributed Tracing (Zipkin/Jaeger). Без цього ви сліпі.

### 3\. Вартість (FinOps)

Managed сервіси, які надають такий рівень абстракції (наприклад, Azure Container Apps або Google Cloud Run), продають обчислювальні ресурси з націнкою (premium).

  * "Голий" VM завжди дешевший за Managed Serverless.
  * Ви платите за зручність розробника грошима компанії.

## Практичне завдання: Думай як Архітектор

У вас є задача: спроектувати систему обробки замовлень для "Чорної п'ятниці".

**Вхідні дані:**

1.  **Сервіс А (Order API):** Приймає замовлення від користувачів. Критична швидкість відповіді.
2.  **Сервіс Б (Notification Worker):** Відправляє email-підтвердження. Швидкість не критична, головне — надійність.

**Архітектурне рішення:**
Де ви застосуєте підхід **Application-First (Dapr)**, а де залишите **Compute-First (Native SDK)**?

<details markdown="1">
<summary>Обґрунтування рішення</summary>

  * **Сервіс А (API):** Краще залишити **Native SDK / Compute-First**.
      * *Чому?* Тут важлива кожна мілісекунда (Latency). Додатковий хоп через Sidecar може уповільнити прийом замовлення під час пікового навантаження. Пряме з'єднання з чергою буде швидшим.
  * **Сервіс Б (Notifications):** Ідеальний кандидат для **Application-First**.
      * *Чому?* Тут важлива простота розробки та надійність (Retries). Якщо поштовий сервіс впаде, Sidecar сам спробує відправити листа пізніше. Затримка в 10-20 мс тут нікого не хвилює. Ми економимо час розробника.

</details>

## Контрольні питання

1.  **Концепція:** У чому головна відмінність "Internal Architecture" (те, що всередині контейнера) від "External Architecture" (те, з чим додаток спілкується)?
2.  **Binding:** Що таке "Binding" в контексті Application-First? Це бібліотека чи API-контракт?
3.  **Performance:** Чому використання Sidecar (наприклад, Dapr) завжди збільшує Latency порівняно з використанням Native Driver? Опишіть шлях запиту.
4.  **Debugging:** Якщо ваша програма спілкується з базою даних через Dapr і база "впала", який Exception ви побачите у своєму Java-коді? Чи буде там інформація про драйвер бази даних?
5.  **Evolution:** Чому, згідно з Ibryam, монолітні додатки стають "анти-патерном" в епоху Application-First?
