# Протокол розробки технічних лекцій великого обсягу (16k+ символів)

> 🇺🇦 Українська версія | 🇬🇧 [English version](./en/10_ai_lectures.md)

Даний документ визначає стандарт ітераційної розробки навчальних матеріалів для запобігання деградації технічної щільності та втрати обсягу через обмеження LLM (RLHF-brevity та Attention Drift).

**Стиль і подача** при переписуванні готових лекцій — у [Правилах редагування лекцій (16)](./16_lecture_editing_rules.md) (не дублювати тут).

---

## 0. Діагностика обмежень (Root Cause)

1. **RLHF-лаконічність:** Моделі навчені видавати стислі відповіді. При запиті на 16к символів модель схильна до "галюцинацій структури" — вона робить вигляд, що написала багато, використовуючи загальні фрази.
2. **Context Window vs Output Token Limit:** Навіть при контексті 200k+, ліміт одного виводу зазвичай обмежений 4k-8k токенами.
3. **Модельна лінь:** При редагуванні великих блоків LLM часто використовує плейсхолдери `[текст залишається незмінним]`, що руйнує цілісність документа.

---

## Етап 1: Архітектурне проектування (Technical Skeleton)

Мета: Створити жорстку матрицю, яка не дозволить моделі відхилятися від заданого обсягу та глибини.

### 1.1. Матриця розподілу обсягу
Кожен розділ повинен мати чіткий ліміт символів. Приклад для лекції на 16,000 символів:

* **Розділ 1: Вступ та постановка проблеми (~1,500 симв.)**
    * Контекст (High-load/Performance).
    * Тези та Core Thesis.
* **Розділ 2: Теоретичний фундамент (~4,500 симв.)**
    * Глибокий аналіз алгоритмів/архітектури.
    * Математичне обґрунтування (LaTeX).
* **Розділ 3: Практична реалізація (~6,000 симв.)**
    * Код (готовий до copy-paste).
    * Оптимізація та FinOps (метрики споживання ресурсів).
* **Розділ 4: Валідація та Кейси (~2,500 симв.)**
    * Benchmarks та Edge Cases.
* **Розділ 5: Висновки та Check-list (~1,500 симв.)**

### 1.2. Технічні вимоги (Constraints)
* **No Generalities:** Заборонено використовувати визначення базових термінів (K8s, O-notation). Тільки специфіка реалізації.
* **Stack-Specific:** Обов'язкова фіксація версій (напр. Python 3.12, PostgreSQL 16).
* **Style:** Expert-to-Expert (прагматично, без епітетів).

## Етап 2: Протокол "Atomic Write" (Інкрементна генерація)

Мета: Обхід ліміту виводу токенів шляхом покрокової збірки.

### 2.1. Правило Buffering (4k Tokens)
Весь процес розбивається на **Stages**. Один запит = один логічний блок (до 4000 символів). 

**Алгоритм дій:**
1. Надати AI "Technical Skeleton".
2. Команда: `Генеруй виключно Розділ 1. Дотримуйся ліміту 1500 символів. Зупинись після завершення`.
3. Команда: `Генеруй Розділ 2. Використовуй контекст Розділу 1, але видавай ТІЛЬКИ новий текст`.

### 2.2. Strict Output Control
При додаванні нових блоків використовувати інструкцію:
> **APPEND MODE:** Видавай тільки нові секції. Категорично заборонено використовувати `...` або скорочувати існуючий текст. Якщо обсяг перевищує ліміт виводу — зупинись і запитай підтвердження на продовження.

## Етап 3: Фіналізація та Quality Assurance (QA)

### 3.1. Валідація розмітки та формул
* Перевірка LaTeX: Всі формули мають бути в $inline$ або $$display$$ (render check).
* Перевірка коду: Відсутність скорочень всередині функцій.
* Markdown-контроль: Правильна ієрархія заголовків (H1 -> H2 -> H3).

### 3.2. Збірка в Markdown-блок
Для зручності копіювання весь фінальний документ (або великий блок) обов'язково загортається у блок коду:
```markdown
[Весь текст лекції тут]

```

## Етап 4: Інструментарій (Agents & IDE)

Для роботи з документами такого обсягу рекомендується використовувати інструменти з прямим доступом до файлової системи:

1. **Cursor (Composer Mode):** * Використовувати `@file` для контексту.
* Промпт: `Update section 3 in @lecture.md. Expand implementation details to 3000 symbols. Keep other sections intact.`
2. **Claude Code (CLI):** * Дозволяє вносити правки через `diff`, що гарантує збереження решти тексту без перегенерації.
3. **Obsidian / VS Code:**
* Для локальної збірки блоків, згенерованих через чат-інтерфейс.
