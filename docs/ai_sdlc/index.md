## Про що цей розділ

Цей розділ розвиває цикл досліджень із керування ШІ-агентами та інженерії програмних проєктів (**AI SDLC**) і присвячений головному вузькому місцю сучасної агентної розробки — **побудові довіреної, версіонованої та багатопрофільної архітектури контексту** у промисловому стеку `Git + Jira + Confluence + TestRail + Infra/APM`.

### Попередні доповіді циклу (Фундамент)
1. **[Управління стохастичними ШІ-агентами: погляд крізь призму прикладної математики та системного аналізу (18)](../18_ai_agent_control_seminar.md)** — перехід від лінійного промптингу до теорії керування (*Plant vs. Controller*), розширення простору станів Маркова (*State Augmentation*), задача оптимальної зупинки Беллмана та детермінована верифікація інваріантів на графах.
2. **[Інженерія програмних проєктів з участю ШІ-агентів (AI SDLC): межі застосовності, парадокси керування та нові системні вузькі місця (19)](../19_ai_sdlc_seminar.md)** — еволюція *Prompt → Context → Harness Engineering*, феномен *Dumb Zone (Lost in the Middle)*, гексагональна архітектура як механізм економії контекстного вікна, парадокс покрокових інструкцій для reasoning-моделей та проблема розсинхронізації продуктового контексту й коду.

## Структура матеріалів розділу

Дослідження архітектури довіреного контексту представлено у двох взаємопов'язаних документах:

### 1. [Інженерний бриф та архітектурні сценарії (Executive Brief + Діаграми)](./01_context_architecture_brief.md)
Концентрований операційний зріз моделі управління контекстом у реальних інженерних командах:
* **Нативні канали ролей, локальні зони та відповідальні артефакти:** розподіл зон володіння між `DEV + Coding Agents`, `QA + QA Agents`, `Perf + Perf Agents`, `PO`, `BA / Arch`, `External 3rd-Party` та `AppSec / SRE`.
* **Природа інструментів:** `Jira` як потік подій змін (*Event Stream / Труба подій*) проти `Confluence` як декларативного стану з явним версіонуванням блоків `As-Is` та `To-Be` і контрактом несуперечливості локальних зон (*Consistency Contract*).
* **Чотири глибокі інженерні дилеми реальної практики:**
  1. Парадокс ізоляції `TestRail` від `DEV` — коли це фіча (*Double-Blind Black-Box Guardrail* проти підгонки коду під тест), а коли бага (пізнє виявлення граничних умов).
  2. Ізоляція Performance-інженерів від бізнес-логіки нових фіч та роль ШІ як двостороннього *Cross-Domain Enabler*-а.
  3. Асиметрія типів змін (малий баг у режимі *Inline All-in-One*, нова фіча *Greenfield* та найважчий випадок — наскрізний *Brownfield Change Request / Deep Bugfix*) і механізм прямого втручання людини (*Human-in-the-Loop Override*).
* **5 детальних діаграм послідовності (Sequence Diagrams + вихідний код PlantUML у згорнутих секціях):**
  * *Діаграма 1:* Наскрізний потік `Jira Event Pipe → Declarative State (Confluence) → Context Assembly за ролями`.
  * *Діаграма 2:* Сценарій `PO + BA + Arch + 3rd-Party` (перетворення шуму чатів і листів на версіонований стан).
  * *Діаграма 3:* Сценарій `DEV + Coding Agent` (три режими роботи: мала зміна, нова фіча, археологія імпакту для масштабного CR).
  * *Діаграма 4:* Сценарій `QA + TestRail` (декларативні граничні умови для DEV проти ізольованих тест-кейсів у TestRail).
  * *Діаграма 5:* Сценарій `Performance Engineer` (ШІ як Enabler, що з'єднує бізнес-фічу з Infra Sizing та NFR).

### 2. [План науково-практичної статті: Багатовимірна таксономія контексту та архітектура пам'яті](./02_context_architecture_plan.md)
Фундаментальне теоретичне й архітектурне обґрунтування:
* **Постановка дослідницького питання та головна теза:** чому векторні бази (*Vector DB*) чи екстрактивні сервіси (*Mem0*) не можуть бути первинним джерелом істини (*Store of Record*), а примус нетехнічних ролей працювати через Git PR у кодових репозиторіях руйнує операційну простоту.
* **Систематизація 10 ролей-споживачів контексту (*Who Needs What Context?*):** детальний розбір специфічних інформаційних потреб розробників, функціонального QA, інженерів продуктивності (NFT), BA/PO, архітекторів, зовнішніх партнерів (3rd-party), фахівців AppSec/Compliance, SRE/Support, Tech Lead рев'юерів та PMO.
* **Восьмивимірна таксономія розрізів контексту (*Context Lenses & Dimensions*):** предметно-фасетний, темпорально-версійний (`As-Is / In-Flight / To-Be / Rejected`), масштабно-структурний (`L1–L4`), епістемічний, модальний, когнітивний, довірчий (`Tier 1–3`) та контурів доступу.
* **Класифікація 4 архітектурних шарів пам'яті та індексів:** порівняльний аналіз *Authoritative Store of Record*, *Lexical BM25*, *Semantic Vector DB (Hybrid RRF)*, *Extractive Memory (Mem0)* та *Temporal Knowledge Graphs (Zep/Graphiti)* на базі досліджень Anthropic (2025–2026, включно з концепцією *Dreaming*), OpenAI (2026), HumanLayer та Letta (*MemFS*, 2026).
* **Цільова прикладна архітектура:** Федеративні першоджерела + виділений *Agent-Compiled Context Hub* та дорожня карта з 7 розділів основної статті з бібліографією.
