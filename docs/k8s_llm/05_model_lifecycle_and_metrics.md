# Методологія: Життєвий Цикл, Метрики та Валідація Моделі

Цей документ описує науковий підхід до тренування та оцінки якості (Evaluation) LLM-асистента.
**Мета:** Отримати кількісні докази ефективності fine-tuning для наукової роботи.

---

## 1. Експериментальний Пайплайн

Ми дотримуємось принципу **Scientific Rigor** (Наукова строгість).

### 1.1 Розподіл Даних
* **Training Set (80%):** Дані для навчання ваг моделі.
* **Validation Set (10%):** Дані для контролю в процесі навчання (щоб уникнути overfitting).
* **Test Set (10% - Hold-out):** "Золотий запас". Модель бачить ці дані *тільки один раз* — під час фінального іспиту.

### 1.2 Життєвий Цикл Версій
| Версія | Опис | Ціль |
| :--- | :--- | :--- |
| **Baseline (Zero-shot)** | Базова модель (Mistral 7B / Llama 3) *без* навчання. | Точка відліку. Показує, наскільки погано працює "ванильна" модель. |
| **v0.1 (Sanity Check)** | Навчання на 50 прикладах. | Перевірка, чи модель вивчила JSON-формат. |
| **v1.0 (Release)** | Навчання на повному датасеті. | Фінальний результат для захисту. |

## 2. Система Метрик (KPIs)

Для наукової роботи ми використовуємо три групи метрик.

### 2.1 Метрики Схожості Тексту (NLP Standard)
Використовуються для автоматичного порівняння згенерованого тексту з еталоном.
* **ROUGE-L:** Оцінює схожість найдовшої спільної підпослідовності. Добре підходить для оцінки `summary`.
* **BLEU Score:** Оцінює точність перекриття n-грам.

### 2.2 Структурні Метрики (JSON Validity)
Критично для інтеграції в програмний комплекс.
* **Format Error Rate (FER):** Відсоток відповідей, які не є валідним JSON.
    * *Ціль:* < 1% для v1.0.
* **Schema Compliance:** Відсоток відповідей, що містять обов'язкові поля (`root_cause`, `recommendation`).

### 2.3 Експертні Метрики (Domain Accuracy)
Це найважливіші метрики для FinOps та SRE. Оцінюються напів-автоматично або вручну.

| Метрика | Формула / Критерій |
| :--- | :--- |
| **Diagnosis Accuracy** | Чи співпадає `root_cause` моделі з еталонним? (True/False) |
| **Hallucination Rate** | Чи вигадала модель параметри, яких не було в Input? (напр., вигадала `P95=500m`, коли в логах `200m`). |
| **Math Consistency** | (Для Right-Sizing) Чи виконується умова: `Recommendation ≈ P95 * 1.2`? |

## 4. Процедура Валідації (Evaluation Script)

Дослідник повинен реалізувати скрипт `evaluate.py`, який:
1.  Бере файл `test.jsonl`.
2.  Генерує відповіді для обох моделей (Base та Fine-Tuned).
3.  Порівнює `root_cause` (Exact Match).
4.  Рахує % валідних JSON.
5.  Зберігає результати у `evaluation_report.csv`.

### Приклад логу валідації (`evaluation_report.csv`)
```csv
sample_id, ground_truth_cause, model_prediction, is_correct, json_valid, math_error
1, OOMKilled, OOMKilled, 1, 1, 0
2, Overcommit, HighCPU, 0, 1, N/A
3, RightSizing, RightSizing, 1, 1, 0.05 (5% deviation)
...
Accuracy: 92%
```

## 5\. Застереження для Наукової Роботи

1.  **Data Leakage:** Суворо стежте, щоб приклади з `test.jsonl` ніколи не потрапляли в `train.jsonl`. Це invalidates (анулює) результати експерименту.
2.  **Reproducibility:** Фіксуйте `random_seed` та гіперпараметри навчання, щоб експеримент можна було відтворити.
