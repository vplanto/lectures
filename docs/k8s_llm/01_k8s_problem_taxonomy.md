# Технічна Таксономія: Діагностика, Оптимізація та Межі

Цей документ визначає **scope (обсяг)** технічних сценаріїв для навчання моделі.
Ми розділяємо задачу на два рівні:
1.  **Діагностика:** Ідентифікація проблеми або неоптимального стану на основі статичних конфігурацій та динамічних метрик.
2.  **Вирішення (Actionable Advice):** Генерація конкретних, числових рекомендацій щодо змін (Right-Sizing, Auto-scaling).

---

## А. Функціональні Відмови (Break-fix Scenarios)
Стани, коли сервіс не працює. Мета рекомендації — відновити працездатність.

### 1. Проблеми Запуску (Startup)
* **Image Pull Issues (`ImagePullBackOff`)**
    * *Діагностика:* Невірний тег, відсутність секрету (`imagePullSecrets`), проблеми реєстру.
    * *Рішення:* Виправити ім'я образу, створити/підключити Secret.
* **Config Dependencies (`CreateContainerConfigError`)**
    * *Діагностика:* Посилання на неіснуючі `ConfigMap` або `Secret`.
    * *Рішення:* Створити відсутні ресурси.
* **CrashLoopBackOff**
    * *Діагностика:* Помилка коду (Exit Code 1), неправильна команда запуску, відсутні змінні середовища.
    * *Рішення:* Виправити `command`/`args`, додати змінні в `env`.

### 2. Проблеми Планування (Scheduling)
* **Resource Shortage (`Pending`)**
    * *Діагностика:* Кластеру не вистачає CPU/RAM для `requests`.
    * *Рішення:* Зменшити `requests` (якщо завищені), увімкнути Cluster Autoscaler або змінити тип інстансу.
* **Affinity/Taint Conflicts**
    * *Діагностика:* Жорсткі обмеження (`requiredDuringScheduling`) блокують розміщення.
    * *Рішення:* Змінити правило на `preferredDuringScheduling`, додати `tolerations`.

### 3. Проблеми Виконання (Runtime)
* **OOMKilled**
    * *Діагностика:* Споживання пам'яті перевищує `limits`.
    * *Рішення:* Підняти `limits.memory` до рівня **P99 + буфер**, або виправити витік пам'яті.
* **Probe Failures**
    * *Діагностика:* Таймаут або помилка (500) на ендпоінті healthcheck.
    * *Рішення:* Збільшити таймінги проб або оптимізувати час старту додатку.

## Б. Неефективність та Оптимізація (Optimization & FinOps)
Сервіс працює, але споживає зайві гроші або має ризики. Мета — **зменшити кости та підвищити стабільність**.

### 4. Інфраструктурна Ефективність (Infrastructure)
* **Node Resource Overcommit**
    * *Діагностика:* Сума `limits` подів на вузлі значно перевищує його ємність (напр., >150%), створюючи ризик непередбачуваного тротлінгу.
    * *Рішення:* Перебалансувати навантаження або додати вузли.
* **Resource Fragmentation (Bin Packing Issue)**
    * *Діагностика:* У кластері достатньо *сумарного* вільного місця, але жоден окремий вузол не може вмістити великий под.
    * *Рішення:* Оптимізація планувальника або використання Descheduler для дефрагментації.
* **Infrastructure Mismatch (Wrong Node Type)**
    * *Діагностика:* Дисбаланс ресурсів (напр., High Memory / Low CPU) на збалансованих інстансах.
    * *Рішення:* Міграція на спеціалізовані сімейства (напр., AWS **r5/r6g** для Memory-bound).
* **Legacy Storage Class**
    * *Діагностика:* Використання дорогих/старих класів (напр., AWS `gp2`).
    * *Рішення:* Міграція на `gp3` (дешевше і продуктивніше).

### 5. Конфігураційна Оптимізація (Quantitative Right-Sizing)
* **Quantitative Right-Sizing (Data-Driven)**
    * *Діагностика:* Значний розрив між `requests` та реальними метриками (Prometheus P95/P99).
    * *Рішення:* Встановити `requests` = `P95 Usage` + **Buffer (15-20%)**.
* **VPA Recommendation (Dynamic Workloads)**
    * *Діагностика:* Навантаження є змінним, статичні `requests` неефективні.
    * *Рішення:* Рекомендувати встановлення **Vertical Pod Autoscaler (VPA)** у режим `recommender` або `auto`.
* **Missing Limits (Noisy Neighbor)**
    * *Діагностика:* Відсутні ліміти (QoS `BestEffort`).
    * *Рішення:* Встановити `limits` для ізоляції.

### 6. Архітектурна Надійність (QoS & HA)
* **Critical Workload QoS Risk**
    * *Діагностика:* База даних або Stateful-сервіс працює в режимі QoS **Burstable** (`requests` < `limits`).
    * *Рішення:* Попередити про ризик OOM/тротлінгу та рекомендувати QoS **Guaranteed** (`requests` == `limits`) для критичних компонентів.
* **Single Availability Zone Risk**
    * *Діагностика:* Всі репліки в одній зоні.
    * *Рішення:* Налаштувати `topologySpreadConstraints`.

## В. Обсяг Рекомендацій (Scope of Solutions)
Модель має надавати відповіді у трьох площинах:
1.  **Зміна параметрів K8s (Manifest Fixes):** `requests`/`limits`, QoS, VPA.
2.  **Зміна Інфраструктури (Infra/Cloud Fixes):** Instance Types, StorageClass.
3.  **Дії Оператора (Human Actions):** Аналіз Prometheus метрик, логів.

---

## Г. Out of Scope (Межі Дослідження)
Виключено з поточного етапу:
1.  **Certificate Management:** Проблеми з cert-manager/TLS.
2.  **Kernel-level debugging:** eBPF, strace.
3.  **Складні Stateful-сценарії:** Реплікація БД (окрім QoS/Storage).

---

## Д. Спеціалізація Моделі (Scope Definition)
**Важливо:** Через виключення мережевої безпеки (Certs) та глибокої діагностики баз даних, розроблюваний LLM-асистент позиціонується як **спеціалізований інструмент для Resource & Configuration Optimization (FinOps + Stability)**. Він не є універсальним "General Purpose SRE Bot" для вирішення всіх типів інцидентів.
