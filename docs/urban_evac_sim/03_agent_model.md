# 03. Agent Architecture

**Scope:** State space definition, Heterogeneity models, and Decision-making logic.
**Input:** Zoning Map (Sources), Graph $G_{opt}$.
**Output:** Agent Objects $A = \{a_1, ..., a_N\}$ initialized for simulation.

## 1. Вектор стану агента (State Space)

Агент у симуляції — це не просто точка $(x,y)$, а скінченний автомат (FSM) з вичерпним внутрішнім ресурсом.
Вектор стану $S_i(t)$ для $i$-го агента:

$$S_i(t) = \langle \mathbf{p}_i(t), g_i, v_i(t), f_i(t), \psi_i(t), \alpha_i(t), \text{class}_i \rangle$$

* $\mathbf{p}_i(t) = (e_{curr}, x_{offset})$: Позиція агента, де:
    * $e_{curr}$: Ідентифікатор поточного ребра (сегмента вулиці).
    * $x_{offset}$: Відстань (наприклад, у метрах) від початкового вузла ребра.
* $g_i \in V_{exit}$: Цільова вершина (зона евакуації).
* $v_i(t)$: Поточна швидкість (обмежена $v_{max}$ авто та $v_{flow}$ потоку).
* $f_i(t) \in [0, 100]$: Залишок палива (%).
* $\psi_i(t) \in [0, 1]$: Рівень стресу/паніки (впливає на ймовірність помилки/агресії).
* $\alpha_i(t) \in \{0, 1\}$: Динамічний коефіцієнт кооперації (Compliance).
* $\text{class}_i$: Тип поведінки (див. п. 2).

### 1.1. Життєвий цикл (FSM States)
Ми працюємо в режимі **"Survival Run"**. В умовах масової евакуації та паніки АЗС вважаються неактивними (паливо вичерпано або недоступне через фізичне блокування під'їздів). Агент має лише той ресурс, з яким стартував.

Агент переходить між станами:
1.  **SPAWNING:** Ініціалізація в зоні `Source`. Очікування слоту в черзі на виїзд.
2.  **MOVING:** Активний рух ($v > v_{thresh}$). Витрата палива пропорційна навантаженню двигуна.
3.  **QUEUED (Idling):** Рух заблоковано затором ($v \approx 0$). Критичний стан: двигун працює, відстань не долається. Саме тут "згорає" більшість агентів.
4.  **FINISHED:** Досяг зони `Sink`. Агент видаляється з пам'яті, метрика $S_{rate}$ інкрементується.
5.  **FAILED (Obstacle):** Паливо вичерпано ($f_i(t) \le 0$) або сталася аварія. Агент зупиняється назавжди, зменшуючи пропускну здатність ребра.

### 1.2. Початкові умови (Resource Scarcity)
Замість моделювання дозаправки, ми вводимо стохастичний розподіл початкового ресурсу. Це симулює реальність, де сигнал тривоги застає водіїв з різним рівнем підготовки.

$$f_{start} \sim \mathcal{U}(f_{min}, f_{max})$$

* **Default:** $f \in [10\%, 90\%]$ від об'єму баку.
* **Game Theory Implication:** Це перетворює задачу на жорсткий тайм-менеджмент. Агент з 15% баку фізично не може пережити 2 години простою в заторі на головній трасі. Це (згідно п. 3.1) автоматично перемикає його в режим **Rogue**, змушуючи шукати ризиковані об'їзди, що парадоксально може врятувати його життя.

## 2. Гетерогенність популяції (Agent Classes)

Ми не моделюємо однорідний натовп. Популяція розділена на класи з різними функціями вартості (Cost Function) для пошуку шляху ($A^*$).

### Class A: Compliant (Слухняні)
* **Частка:** ~70-80% (параметр сценарію).
* **Логіка:** Суворо дотримується ПДР.
* **Cost Function:**
    $$Cost(e) = W_{static}(e) + W_{traffic}(e)$$
    Якщо $type(e) == \text{forbidden}$ (зустрічна смуга/тротуар), то $Cost(e) \to \infty$.
* **Re-routing:** Тільки при отриманні зовнішньої команди (Broadcast) або повному блокуванні шляху.

### Class B: Rogue/Aggressive (Порушники)
* **Частка:** ~20-30%.
* **Логіка:** Мінімізація власного часу за будь-яку ціну.
* **Cost Function:**
    $$Cost(e) = W_{static}(e) + \alpha \cdot W_{traffic}(e) + P_{risk}$$
    Де $P_{risk}$ — малий штраф за порушення. Вони "бачать" зустрічні смуги та узбіччя як валідні ребра з підвищеною вартістю, але не нескінченною.
* **Re-routing:** Жадібний (Greedy). Перераховує маршрут кожні $N$ тіків, якщо швидкість падає нижче порогу.

## 3. Логіка прийняття рішень (Decision Loop)

На кожному кроці симуляції ($\Delta t = 1s$) агент виконує цикл OODA (Observe-Orient-Decide-Act).

### 3.1. Observe (Сприйняття)
Агент "бачить" тільки локальну інформацію:
* Швидкість потоку на поточному ребрі $v_{flow}(e_{curr})$.
* Візуальний контакт із затором попереду (на глибину $k$ ребер).
* *Тільки для Class A:* Отримує глобальні метрики від "System Controller" (якщо увімкнено).

### 3.2. Decide (Планування)
Рішення про зміну маршруту приймається на основі **Tension Index** ($I_T$):

$$I_T = \frac{T_{expected}}{T_{baseline}}$$

* Якщо $I_T > \text{Tolerance Threshold}$ (наприклад, затримка > 50%), агент ініціює перерахунок шляху ($A^*$).
* **Class B** має нижчий поріг толерантності (швидше починає шукати об'їзд), що часто призводить до осциляцій та створення нових заторів на другорядних дорогах.

## 4. Фізичні профілі (Vehicle Physics)

Для реалістичності ми використовуємо різні типи транспортних засобів:

| Attribute | Sedan (60%) | SUV (30%) | Truck (10%) |
| :--- | :--- | :--- | :--- |
| **Length** | 4.5 m | 5.0 m | 12.0 m |
| **Tank Size** | 50 L | 70 L | 300 L |
| **Idle Burn** | 0.8 L/h | 1.2 L/h | 2.5 L/h |
| **Aggression**| Low | High | Low |

* **Довжина** впливає на те, як швидко заповнюється ребро (Capacity Consumption).
* **Idle Burn** критичний для сценаріїв тривалих заторів.

## 5. Implementation Notes (Технічні деталі)

Для оптимізації Python-коду:
1.  **Lazy Pathfinding:** Не перераховувати маршрути всім одночасно. Використовувати чергу запитів на перерахунок з лімітом (Budget) на тик.
2.  **Shared Memory:** Маршрути зберігаються як списки ID ребер. Граф не копіюється для кожного агента.
3.  **Spatial Hashing:** Для перевірки "хто поруч" не використовувати перебір $O(N^2)$. Агенти реєструються у своїх ребрах, ребро знає список агентів.
