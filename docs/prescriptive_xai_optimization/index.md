### Анотація
Предиктивний аналіз каже: "Завтра сервер впаде". Прескриптивний аналіз каже: "Збільши RAM на 4GB або відкати реліз `v2.4`". Цей курс вчить будувати системи, що пояснюють свої рішення. Ми розберемо архітектуру порівняльного аналізу (на базі реальних специфікацій компаній), теорію ігор (Shapley Values) та методи контрфактуального мислення, щоб перетворити "Чорну скриньку" на прозорий інструмент прийняття рішень.

> **📚 Новий у DevOps?** Почніть з [Глосарію курсу](./11_course_glossary.md) — там пояснено всі терміни через аналогії та приклади.

#### Вступ: Феномен "Розумного Ганса"
Чому висока точність (Accuracy) може бути брехнею. Проблема довіри до "Чорних скриньок".

* **[00_clever_hans_effect.md](./00_clever_hans_effect.md)**
    * **Тема:** Ефект Розумного Ганса та пастка кореляцій.
    * **Зміст:** Історія коня, що обдурив науку. Приклад з "Вовками та Хаскі" (LIME). Чому AI вчиться чітерити, а не розуміти фізику процесу. Введення в XAI (eXplainable AI).

#### Блок 1: Архітектура Діагностики (Differential Analysis)
*Базується на логіці `Comparison` з Tech Spec.*
Як знайти проблему шляхом порівняння "Здорового" (Base) та "Хворого" (Target) станів.

* **[01_comparative_architecture.md](./01_comparative_architecture.md)**
    * **Тема:** Архітектура порівняльного аналізу (A/B Testing on Steroids).
    * **Зміст:** Як порівнювати складні системи?
        * **Base vs Target:** Концепція Baseline.
        * **Delta Metrics:** Абсолютна та відносна різниця (`abs_diff`, `rel_diff`).
        * **Thresholding:** Як визначити "значущу" деградацію (Soft/Hard thresholds).
    * **Практика:** Парсинг JSON-репортів та побудова таблиці відхилень (аналог логіки з Tech Spec).

#### Блок 2: Відповідь на питання "Чому?" (Interpretability)
Математика пояснення.

* **[02_game_theory_shapley.md](./02_game_theory_shapley.md)**
    * **Тема:** Значення Шеплі (Shapley Values).
    * **Зміст:** Теорія ігор: як чесно розділити виграш між гравцями. "Гравці" = ознаки (CPU, DB_Calls, Network). "Виграш" = відхилення від прогнозу.
    * **SHAP (SHapley Additive exPlanations):** Глобальна vs Локальна інтерпретація. Чому `Latency` виросла? (Бо `DB_Calls` додали +200ms, а `CPU` зменшило на -50ms).

* **[03_lime_local_approximation.md](./03_lime_local_approximation.md)**
    * **Тема:** LIME (Local Interpretable Model-agnostic Explanations).
    * **Зміст:** Ідея: апроксимувати складну нейромережу простою лінійною моделлю *локально* навколо точки інтересу. Як пояснити окрему аномалію.

#### Блок 3: Прескриптивний Аналіз (Actionable Advice)
Генерація рецептів виправлення.

* **[04_counterfactual_analysis.md](./04_counterfactual_analysis.md)**
    * **Тема:** Контрфактуальне мислення ("Що, якби?").
    * **Зміст:** Пошук мінімальної зміни входу, щоб змінити вихід.
    * **Задача:** "Що треба змінити в конфігурації (RAM, Threads), щоб Latency повернулася в норму (< 200ms)?".
    * **Алгоритм:** DiCE (Diverse Counterfactual Explanations).

#### Блок 4: Практикум (Workshop)
Створення "Performance Doctor".

* **[05_building_performance_doctor.md](./05_building_performance_doctor.md)**
    * **Тема:** Інтеграція: Comparator + SHAP + Prescription.
    * **Зміст:**
        1.  **Ingestion:** Завантаження двох профайлів (Base/Target).
        2.  **Detection:** Виявлення деградації > 10%.
        3.  **Diagnosis:** SHAP показує, що причина — "Memory Leak" у модулі `Auth`.
        4.  **Prescription:** Система генерує тікет: "Рекомендовано збільшити Garbage Collection rate".

#### Блок 5: Практична реалізація (Implementation)
Три семінари з повною реалізацією системи моніторингу на базі статистичних інваріантів.

* **[07_seminar1_invariant_discovery.md](./07_seminar1_invariant_discovery.md)**
    * **Тема:** Математичне моделювання та пошук інваріантів.
    * **Зміст:**
        * **Методологія:** Замість статичних порогів — статистичні інваріанти (стійкі лінійні залежності між групами метрик).
        * **Математика:** PCA для зменшення розмірності (≥95% варіативності), лінійна регресія для пошуку інваріантів y=ax+b, детекція аномалій через порівняння залишків.
        * **Реалізація:** Клас `InvariantDiscovery` з повним pipeline від PCA до детекції порушень.
    * **Практика:** Виявлення інваріантів між CPU, Memory та Network метриками.

* **[08_seminar2_shap_lime.md](./08_seminar2_shap_lime.md)**
    * **Тема:** Діагностика розриву інваріантів через SHAP та LIME.
    * **Зміст:**
        * **Методологія:** Пояснення порушень інваріантів через адитивні внески ознак.
        * **Математика:** Значення Шеплі (Shapley Values) з теорії ігор, KernelSHAP для апроксимації, LIME для локальної інтерпретації.
        * **Реалізація:** Класи `KernelSHAPExplainer`, `LIMExplainer`, `InvariantDiagnostics` з waterfall візуалізацією.
    * **Практика:** Розподіл "провини" за порушення інваріанта між окремими метриками.

* **[09_seminar3_performance_doctor.md](./09_seminar3_performance_doctor.md)**
    * **Тема:** Контрфактуальна терапія та прескриптивний аналіз.
    * **Зміст:**
        * **Методологія:** Перетворення діагнозу "Чому це сталося" на дієву пораду "Що змінити".
        * **Математика:** Оптимізаційна задача пошуку контрфактуалів (мінімальна відстань + задоволення інваріанта), DiCE для генерації різноманітних рішень.
        * **Реалізація:** Клас `PerformanceDoctor` з методами `find_counterfactual`, `prescribe_solution`, форматування рекомендацій.
    * **Практика:** Генерація конкретних рекомендацій типу "Зменш параметр А на 15%, щоб відновити стабільність інваріанта Б".

* **[10_stability_evaluation.md](./10_stability_evaluation.md)**
    * **Тема:** Stability Evaluation: Оцінка стабільності пояснень (Robustness).
    * **Зміст:**
        * **Методологія:** Обов'язковий етап валідації системи Performance Doctor. Оцінка стабільності пояснень (SHAP, LIME) через bootstrap sampling, perturbation analysis та agreement між методами.
        * **Математика:** Метрики стабільності (Robustness Score, CV Score, Rank Stability, Top-K Stability, Agreement Score). Критерії валідації для production.
        * **Реалізація:** Клас `StabilityEvaluator` з інтеграцією в `PerformanceDoctor`. Автоматична корекція впевненості на основі стабільності.
    * **Практика:** Перевірка стабільності пояснень перед застосуванням рекомендацій у production.

* **[06_future_causal_inference.md](./06_future_causal_inference.md)**
    * **Тема:** Кореляція $\neq$ Причинність.
    * **Зміст:** Вступ до Causal Inference (Judea Pearl). Графи причинності (DAGs). Чому XAI — це лише перший крок до справжнього розуміння причин.
