### Гайд для самостійного вивчення: Від «Чорної скриньки» до автоматичного «Performance Doctor»

Цей гайд допоможе тобі зрозуміти, чому висока точність моделі може бути ілюзією (ефект Розумного Ганса), як математично «розсудити» внесок різних метрик у збій системи та як перетворити сухі цифри моніторингу на конкретні рецепти лікування IT-інфраструктури.

> **💡 Порада:** Перед початком вивчення обов'язково прочитай [Глосарій курсу](./11_course_glossary.md) — там пояснено всі терміни через аналогії та приклади.

#### 1. Вступ: Пастка «Розумного Ганса» та криза довіри
Традиційний ML часто працює як **Black Box (Чорна скринька)**: ми бачимо прогноз, але не знаємо причин. Це створює ризики для бізнесу та регуляції (GDPR).

**📖 Матеріали курсу:**
*   **[00_clever_hans_effect.md](./00_clever_hans_effect.md)** — детальна історія ефекту Розумного Ганса та приклади з реальних систем
*   **[06_future_causal_inference.md](./06_future_causal_inference.md)** — поглиблене вивчення причинно-наслідкових зв'язків

**Ключові концепції для вивчення:**
*   **Ефект Розумного Ганса:** Ситуація, коли модель досягає високої точності, використовуючи приховані підказки (кореляції), а не реальне розуміння задачі (наприклад, розпізнавання вовка за снігом на фоні). Детальніше → [00_clever_hans_effect.md](./00_clever_hans_effect.md)
*   **Кореляція ≠ Причинність:** SHAP та LIME показують асоціації, але лише **Causal Inference** (причинно-наслідковий висновок) дозволяє зрозуміти, чи дійсно зміна параметра виправить проблему. Поглиблене вивчення → [06_future_causal_inference.md](./06_future_causal_inference.md)

#### 2. Архітектурний фундамент: Порівняльний аналіз та інваріанти
Замість того, щоб гадати, ми порівнюємо «здорову» версію системи (**Baseline**) з «хворою» (**Target**).

**📖 Матеріали курсу:**
*   **[01_comparative_architecture.md](./01_comparative_architecture.md)** — архітектура порівняльного аналізу та Comparator Engine
*   **[07_seminar1_invariant_discovery.md](./07_seminar1_invariant_discovery.md)** — практична реалізація пошуку інваріантів

**Що опрацювати:**
*   **Статистичні інваріанти:** Стійкі математичні залежності між метриками, що зберігаються у нормальному стані. Практична реалізація → [07_seminar1_invariant_discovery.md](./07_seminar1_invariant_discovery.md)
*   **PCA (Метод головних компонент):** Твій інструмент для зменшення розмірності. Він знаходить «головні напрямки» у даних, що пояснюють ≥95% варіативності. Детальніше → [07_seminar1_invariant_discovery.md](./07_seminar1_invariant_discovery.md)
*   **Comparator Engine:** Архітектурний компонент, що обчислює дельти (Delta Metrics) та визначає значущість відхилень через пороги (Thresholds). Архітектура → [01_comparative_architecture.md](./01_comparative_architecture.md)

#### 3. Математика пояснення: Теорія ігор та локальна простота
Коли система «хворіє», нам потрібно справедливо розподілити «провину» між ознаками (CPU, DB_calls, RAM).

**📖 Матеріали курсу:**
*   **[02_game_theory_shapley.md](./02_game_theory_shapley.md)** — теорія значень Шеплі та SHAP
*   **[03_lime_local_approximation.md](./03_lime_local_approximation.md)** — метод LIME для локальної інтерпретації
*   **[08_seminar2_shap_lime.md](./08_seminar2_shap_lime.md)** — практична реалізація діагностики через SHAP та LIME

**Математичні вузли:**
*   **Значення Шеплі (Shapley Values):** Концепція з теорії кооперативних ігор. Вона визначає **маржинальний внесок** кожної ознаки в фінальний прогноз моделі. Теорія → [02_game_theory_shapley.md](./02_game_theory_shapley.md)
*   **SHAP (Shapley Additive exPlanations):** Бібліотека, що реалізує адитивне пояснення. Сума всіх SHAP-значень дорівнює різниці між прогнозом та базовим значенням (властивість ефективності). Детальніше → [02_game_theory_shapley.md](./02_game_theory_shapley.md), практика → [08_seminar2_shap_lime.md](./08_seminar2_shap_lime.md)
*   **LIME:** Метод, що будує просту лінійну модель **локально** навколо конкретної аномалії, щоб пояснити складну нелінійну систему. Теорія → [03_lime_local_approximation.md](./03_lime_local_approximation.md), практика → [08_seminar2_shap_lime.md](./08_seminar2_shap_lime.md)

#### 4. Прескриптивний аналіз: Мислення «Що, якби?»
Ми переходимо від діагнозу («чому це сталося») до терапії («що змінити») за допомогою **контрфактуального аналізу**.

**📖 Матеріали курсу:**
*   **[04_counterfactual_analysis.md](./04_counterfactual_analysis.md)** — теорія контрфактуального аналізу
*   **[09_seminar3_performance_doctor.md](./09_seminar3_performance_doctor.md)** — практична реалізація прескриптивного аналізу
*   **[05_building_performance_doctor.md](./05_building_performance_doctor.md)** — інтеграція всіх компонентів у систему Performance Doctor

**Алгоритм побудови рекомендацій:**
*   **Контрфактуал (Counterfactual):** Пошук такого стану системи ($x_{cf}$), який максимально близький до поточного, але дає бажаний результат (наприклад, Latency < 200ms). Теорія → [04_counterfactual_analysis.md](./04_counterfactual_analysis.md)
*   **DiCE (Diverse Counterfactual Explanations):** Генерація декількох різноманітних варіантів вирішення проблеми, щоб адміністратор міг обрати найбільш реалістичний. Детальніше → [04_counterfactual_analysis.md](./04_counterfactual_analysis.md), практика → [09_seminar3_performance_doctor.md](./09_seminar3_performance_doctor.md)
*   **Actionable Features:** Фільтрація ознак, які ми дійсно можемо змінити (наприклад, ліміт пам'яті), від тих, що нам непідвладні (наприклад, ID користувача). Практична реалізація → [09_seminar3_performance_doctor.md](./09_seminar3_performance_doctor.md)
