# Правила редагування лекцій

> 🇺🇦 Українська версія | 🇬🇧 [English version](./en/16_lecture_editing_rules.md)

**Доповнює** [протокол розробки з ШІ (10)](./10_ai_lectures.md) (процес, Atomic Write, QA) правилами **стилю та подачі** при переписуванні готових лекцій.

**Scope:** лекції та семінари в `docs/**` (файли `NN_*.md`, `lecture_*.md`, `SEMINARS_README.md`).  
**Не стосується:** НМК (`methodology.md`, `sources.md`, `DISCLAIMER.md`), `index.md`, `study_materials.md`, `material_study.md`.

**Головний принцип:** перепис ≠ скорочення. Міняємо **подачу** (hook, ритм, ієрархія), але **не викидаємо** навчальний зміст.

---

## 1. Стиль тексту (Anti-LLM)

- **Без шаблонів:** жодних «Вступів», «Висновків», «Важливо зазначити», «Ключовий висновок».
- **In medias res:** лекція починається з інциденту, бага або неочевидного компромісу — не з «Мета лекції».
- **Теорія = інструмент:** розділи пояснюють, як розібрати інцидент з відкриття; порядок можна змінити, **обсяг пояснень — ні**.
- **Рваний ритм:** довге технічне речення. Коротке. Ударне. **Але коротке речення — не заміна абзацу пояснення.**
- **Subway Test:** абзац ≤ 4 рядки. Якщо думка не вміщається — **новий абзац**, а не викидання деталей.
- **Жирним** — лише ключові змінні, концепти, вузли системи (не цілі речення).

### 1.1. Anti-LLM ≠ telegraphese

**Заборонено** перетворювати лекцію на telegram-стиль:

| Було в оригіналі (зберегти зміст) | Неправильно при переписі |
|-----------------------------------|---------------------------|
| Розгорнутий абзац про Kleppmann / CAP у блокчейні | Один рядок «компроміс реальний» |
| Пояснення «чому 3 vs 4 вузли» для pBFT | Лише формула $N \ge 3f+1$ |
| Кейс Bitcoin Cash, березень 2013, CBECI, The Merge | Одне речення без деталей |
| Блок «що відбувається з клієнтом при падінні лідера» | Видалити повністю |

**Правило:** якщо в оригіналі був абзац, цитата, `>`-блок або розгорнута відповідь — він лишається (можна перефразувати стилем, **не скорочувати** без явного запиту).

## 2. Обсяг тексту (не скорочувати)

### 2.1. Мінімальний обсяг

Після перепису лекції:

- **≥ 90%** слів (або рядків prose) від оригіналу — орієнтир.
- **100%** обов'язкових блоків з розділу 4.3.
- Кожен алгоритм / протокол зберігає: **логіку**, **проблему**, **production-приклади**, **посилання на симулятор** (якщо були).

### 2.2. Що не можна вирізати «заради стилю»

- Історичні кейси (Bitcoin Cash, fork 2013, Binance тощо).
- Інженерні примітки (`> ...`, «Чому 3 vs 4 вузли», «Що таке The Merge»).
- Розгорнуті пояснення CAP для хмари **і** для блокчейну (обидва контексти).
- Числа, метрики, посилання (CBECI, whitepaper, IRC-чат).
- Екзаменаційні відповіді та міні-кейс.

### 2.3. Як скорочувати довгі абзаци правильно

Не викидати — **дробити** на кілька абзаців по ≤ 4 рядки.

## 3. Мова та терміни

### 3.1. Мова prose: українська

**Основний текст лекції — українською.** Англійська дозволена лише там, де без неї не обійтися:

| Дозволено латиницею | Замість англіцизму в реченні |
|--------------------|------------------------------|
| Імена: **Bitcoin**, **AWS**, **Gilbert & Lynch** | ~~healing~~ → **відновлення зв'язку** |
| Абревіатури після пояснення: **CAP**, **PoW** | ~~crash~~ → **збій вузла** |
| Код і API: `SELECT`, `DELETE FROM`, `200 OK` | ~~trade-off~~ → **компроміс** |
| Усталені назви протоколів: **Raft**, **pBFT** | ~~split-brain~~ → **роздвоєння стану** (далі — переважно українською) |

**Тест:** прочитай абзац вголос. Якщо кожне друге слово англійською — переписати.

### 3.2. Перша згадка терміна

При **першій** згадці англомовного терміна — **українське пояснення в дужках**:

```markdown
**consensus** (консенсус — узгодження стану між вузлами)
**partition** (розрив мережі — вузли не бачать один одного)
```

- Повторні згадки: **переважно український відповідник**; англійську лишати для усталених абревіатур (**CAP**, **BFT**).
- Не дублювати пояснення в дужках на кожному рядку.

### 3.3. Без зайвих англіцизмів

| Не так | Так |
|--------|-----|
| `region` | **регіон** |
| `Краще halt, ніж два truth` | *Краще зупинитися, ніж мати дві версії правди* |
| `після healing` | **після відновлення зв'язку** |

### 3.4. Чиста кирилиця

**Заборонено** змішувати латиницю та кирилицю в одному слові.

## 4. Педагогіка та структура

### 4.1. Hook ≠ міні-кейс

- Hook — **інший** інцидент, ніж міні-кейс на 1 бал.
- Hook **не** дає готової відповіді на міні-кейс.

### 4.2. Питання лише про вже відоме або загальне

- Не питати про **Raft** до розділу про **Raft**.
- У `<details>`: кожен пункт = **питання + відповідь**.

### 4.3. Збереження навчального скелета

Зберігати **повністю** (зміст, не лише заголовки):

- таблиці, код, формули;
- HTML-блоки симуляторів;
- цитати та блоки `>` з інженерними примітками;
- екзаменаційний блок, Definition of Done, міні-кейс.

## 5. Приклади

- **Production-ready:** mempool, CEX, Foundry, TRC-20/ERC-20, роздвоєння стану в банку.
- **Не використовувати:** Foo/Bar, Animal/Dog.

## 6. Мета-заголовки лекції

```markdown
# Лекція N. [Коротка назва]

**Фаза:** Concept | **Далі:** [наступна лекція](./...)
**Симулятори / Артефакт:** [посилання]
```

Без «Мета:» — але **без втрати** змісту, який раніше був у вступі.

---

## 7. Scope змін

- Мінімальний diff за задачею.
- Без git commit без явного прохання.

---

## 8. Чеклист перед здачею лекції

**Стиль**
- [ ] Hook не спойлерить міні-кейс
- [ ] Кутові питання не посилаються на ще не введений матеріал
- [ ] Абзаци ≤ 4 рядки (**дроблення**, не **видалення**)

**Мова**
- [ ] Prose українською; англійська — лише імена, абревіатури, код
- [ ] Немає telegraphese (ланцюжків англійських іменників)
- [ ] Перша згадка терміна — з українським поясненням
- [ ] Немає змішаних слів (кирилиця + латиниця)

**Обсяг**
- [ ] Prose ≥ ~90% оригіналу (перевірити diff / word count)
- [ ] Усі кейси, примітки `>`, формули, симулятори на місці
- [ ] Кожен алгоритм: логіка + production + практика (якщо було)

**Технічне**
- [ ] Таблиці, формули, HTML без спотворень
- [ ] Екзамен-блок і міні-кейс без змін (якщо не просили)
