# Боротьба з Alert Fatigue: Байєсівська логіка фільтрації

## 1. Фундамент: Від парадоксу до SRE-практики

**Diagnosis:** Основна причина ігнорування сповіщень (Alert Fatigue) — це не поганий інструментарій, а математична пастка базової частоти (Base Rate Fallacy). Коли критичні збої трапляються рідко (напр. 0.01%), навіть система моніторингу з 99% точністю генерує понад 90% помилкових тривог.

Для ефективного Observability необхідно розуміти математичний зв'язок між апріорною ймовірністю збою та достовірністю алерту.

### Рекапітуляція математичного апарату
Згідно з теоремою Байєса, ймовірність того, що інцидент є критичним за умови отримання алерту $P(Crit \mid Alert)$, розраховується як:

$$P(Crit \mid Alert) = \frac{P(Alert \mid Crit) \cdot P(Crit)}{P(Alert)}$$

де:
* $P(Crit)$ — базова частота (Base Rate) критичних збоїв у системі.
* $P(Alert \mid Crit)$ — чутливість (Sensitivity) моніторингу (ймовірність алерту при реальному збої).
* $P(Alert)$ — повна ймовірність отримання алерту (включаючи шум).

## 2. Моделювання фільтрації у Kubernetes

У розподілених системах ми маємо справу з екстремальним дисбалансом класів (Extreme Class Imbalance). Кількість нормальних подій перевищує кількість збоїв у $10^4$ або $10^6$ разів.

**Diagnosis:**
Якщо ви налаштовуєте алерт на кожне виключення (Exception) у логах, ви створюєте систему з низьким показником Precision. Навіть якщо ваш класифікатор (напр. Naive Bayes) має високу Accuracy, він буде марним для інженера через Alert Fatigue.

**Actionable Advice:**
1. **Використовуйте MCC (Matthews Correlation Coefficient):** Це "золотий стандарт" оцінки моніторингу на незбалансованих даних, оскільки він враховує True Negatives (нормальну роботу).
2. **Агрегація за вікном (Windowing):** Байєсівська ймовірність збою зростає експоненційно при повторенні сигналу. Один `ERROR` — це шум, 10 `ERROR` за 1 секунду — це сигнал з високим $P(Crit \mid Alert)$.
3. **Контекстна фільтрація:** Використовуйте семантичні ознаки (embeddings) для розрізнення "очікуваних помилок" від аномалій.

### Hidden Risks
Спроба максимально знизити False Positives (шум) математично неминуче призводить до зростання False Negatives (пропущених збоїв). У критичних системах (напр. фінансові транзакції) цей trade-off зміщується у бік "краще перевірити зайве", що вимагає впровадження автоматизованої первинної діагностики (AI-SRE) для розвантаження людей.
