# LLM для діагностики інцидентів: Побудова Smart Runbooks

## 1. LLM як оркестратор Спостережуваність (Observability) Pipeline

### Факт

 Традиційні Runbooks (інструкції з виправлення) — статичні документи, які швидко застарівають і часто не враховують специфічний контекст поточного інциденту. Великі мовні моделі (LLM) можуть динамічно синтезувати знання з метрик, логів та минулого досвіду для генерації точних кроків виправлення (Prescriptive Analytics).

### Чому LLM не можна використовувати "в лоб":
* **Галюцинації:** Без заземлення на реальні дані модель може вигадати неіснуючі параметри конфігурації Kubernetes.
* **Брак актуальності:** LLM навчена на застиглих даних і не знає про зміни в інфраструктурі, що відбулися 5 хвилин тому.
* **Конфіденційність:** Відправка сирих логів у публічні API (напр. OpenAI) несе ризики витоку персональних даних або секретів.

## 2. Архітектура RAG (Retrieval-Augmented Generation)

Для вирішення проблем галюцинацій використовується архітектура **RAG**. Вона перетворює LLM з "генератора тексту" на "інтелектуального аналітика", що працює з вашою базою знань.

### Компоненти системи:
1.  **Vector Store:** Сховище ембеддінгів минулих інцидентів, постмортемів та документації.
2.  **Context Retriever:** Коли стається алерт, система шукає у Vector DB найбільш схожі ситуації за допомогою косинусної схожості.
3.  **Augmented Prompt:** LLM отримує промпт, що містить:
    * Поточні аномальні метрики (Блок 1).
    * Класифіковані BERT-ом логи (Блок 3).
    * Релевантні уривки з Runbooks.

---

## 3. Практикум: Створення "Розумного" Промпту

### Рекомендація

 Ефективність діагностики залежить від структури вхідного контексту. Використовуйте результати кореляції TraceID для побудови ланцюжка доказів.

```python
def generate_incident_report(alert_data, bert_summary, recovered_docs):
    """
    Формування контексту для LLM-діагноста.
    """
    prompt = f"""
    ROLE: Senior SRE Engineer.
    TASK: Analyze the incident and provide a 3-step mitigation plan.
    
    CURRENT ALERT: {alert_data['name']} (P99 Затримка (Latency) > 2s)
    INFLECTION POINT (t0): Detected at minute {alert_data['t0']}
    
    BERT LOG CLASSIFICATION: 
    - Category: {bert_summary['category']}
    - Confidence: {bert_summary['confidence']}%
    - Key Patterns: {bert_summary['patterns']}
    
    RELEVANT RUNBOOK EXCERPTS:
    {recovered_docs}
    
    OUTPUT FORMAT: 
    1. Diagnosis (Why it happened)
    2. Actionable Steps (What to do now)
    3. Verification (How to check if it's fixed)
    """
    return prompt

```

## 4. Hidden Risks та Етика AI-SRE

* **Data Privacy:** Перед відправкою контексту в LLM необхідно проводити **Sanitization** — автоматичне видалення IP-адрес, токенів та імен користувачів за допомогою regex або спеціалізованих моделей.
* **Confirmation Bias:** Якщо LLM видає дуже впевнену, але помилкову відповідь, інженер може проігнорувати очевидні суперечливі сигнали в метриках. Завжди вимагайте від моделі надання посилань на первинні дані (метрики/логи).
* **Cost of Tokens:** Постійний аналіз мільйонів логів через LLM є економічно недоцільним. Використовуйте LLM лише на фінальному етапі, коли Блок 1 та Блок 2 вже підтвердили наявність реального інциденту.

---

**Steelmanning:**
Критики стверджують, що досвідчений інженер швидше знайде причину через `kubectl logs` та `dashboard`. **Counter-argument:** У системах з 500+ мікросервісів жоден інженер не володіє повним контекстом. LLM виступає як "когнітивний підсилювач", який миттєво згадує інцидент річної давнини в іншому сервісі, що має таку ж математичну модель розпаду.
