# Семантичний аналіз інцидентів: Текст як вектор (Embeddings)

## 1. Проблема синонімів та лінгвістичного шуму

### Факт

 Традиційні методи моніторингу (напр. Naive Bayes або grep) провалюються, коли одна і та сама технічна проблема описується різними словами. Наприклад, повідомлення `Database connection failed` та `DB link is down` мають ідентичну причину (Першопричина (Root Cause)), але для статистичних методів це абсолютно різні набори токенів.

### Чому "мішок слів" (BoW) не працює для діагностики:
* **Брак контексту:** BoW не бачить різниці між `Connection refused` та `Connection established`.
* **Висока розмірність:** Кожен унікальний ID або хеш у логах створює новий вимір у просторі ознак, розмиваючи сигнал.
* **Лексичний розрив:** Система не розуміє, що `OOMKilled` та `Out of Memory` — це одна й та сама сутність.

## 2. Геометрія змісту: Вступ до Embeddings

Для вирішення проблеми ми переходимо від підрахунку слів до **векторних представлень (Embeddings)**.

**Суть методу:** Кожне лог-повідомлення перетворюється на вектор у багатовимірному просторі $R^N$ (де $N$ зазвичай дорівнює 768 для моделей типу BERT).

### Математична логіка:
Якщо два повідомлення мають схожий зміст, відстань між їхніми векторами у просторі буде мінімальною. Найчастіше для цього використовується **Косинусна схожість (Cosine Similarity)**:

$$\text{similarity} = \cos(\theta) = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|}$$

### Рекомендація


Використовуйте семантичний пошук для "дедуплікації" алертів. Якщо новий інцидент має косинусну схожість $> 0.9$ з уже існуючим відкритим тікетом, система має автоматично їх групувати, запобігаючи Втома від сповіщень (Alert Fatigue).

## 2.1 Математична пастка: Euclidean ($L_2$) vs Cosine у $R^{768}$

### Факт

 У високонавантажених системах довжина логу (Magnitude) часто залежить від рівня дебагу, а не від суті проблеми. Евклідова відстань вимірює довжину вектора, тоді як Косинусна схожість — його напрямок (семантику).

### Порівняння метрик на прикладі "Семантичних двійників"

Розглянемо три вектори логів у просторі $R^{768}$:
* **A:** `Error: timeout` (Короткий вектор, напрямок: Failure)
* **B:** `Error: timeout; stacktrace: [5000 chars...]` (Дуже довгий вектор, напрямок: Failure)
* **C:** `Success: request processed` (Короткий вектор, напрямок: Success)

| Пара логів | Семантичний зв'язок | Euclidean ($L_2$) | Cosine Similarity |
| :--- | :--- | :--- | :--- |
| **A** та **B** | **Ідентичні** (Failure) | **Величезна** (через довжину) | **~1.0** (той самий кут) |
| **A** та **C** | **Різні** (Fail vs OK) | **Мала** (обидва короткі) | **~0.0** (різні кути) |


**Висновок для інженера:**
Якщо ви використовуєте $L_2$ (напр. у кластеризації k-means без нормалізації), ваша система Спостережуваність (Observability) скаже, що **короткий Error (A)** ближче до **короткого Success (C)**, ніж до свого **двійника з дебаг-інфою (B)**[cite: 90, 107].

### Математична нормалізація
Для того, щоб зробити $L_2$ придатною для SRE, вектори мають бути нормалізовані до одиничної довжини ($\|\mathbf{A}\| = 1$). У такому разі $L_2$ стає монотонно пов'язаною з Cosine Similarity:
$$d_{L2}(\mathbf{A}, \mathbf{B})^2 = 2 - 2 \cdot \cos(\theta)$$
Проте в задачах NLP/Спостережуваність (Observability) стандартним "золотим правилом" залишається використання **Cosine Similarity** за замовчуванням.


## 3. Від Word2Vec до Contextual Embeddings: Проблема контексту

### Факт

 Перше покоління векторних моделей (напр., Word2Vec, GloVe) створювало **статичні ембеддінги** — кожне слово мало один фіксований вектор незалежно від оточення. Це робило їх майже такими ж "наївними", як і Байєсівські класифікатори, у ситуаціях, де технічний термін змінює значення залежно від дієслова поруч.

### Чому статика провалюється в SRE:
Розглянемо два лог-повідомлення:
1. `Connection established successfully` (Normal)
2. `Connection refused by database` (Critical)

У моделі Word2Vec слово `Connection` матиме ідентичний вектор в обох випадках. Оскільки це слово зустрічається дуже часто в обох класах, воно стає "семантичним шумом".

### Рішення: Контекстуалізація через BERT
Моделі типу **BERT (Bidirectional Encoder Representations from Transformers)** використовують механізм **Self-Attention**. Це дозволяє динамічно змінювати вектор слова залежно від усіх інших слів у реченні.

**Математична інтуїція:**
Вектор слова $w_i$ обчислюється як зважена сума векторів усіх слів у контексті:
$$\mathbf{h}_i = \sum_{j} \alpha_{i,j} (V \mathbf{x}_j)$$
Де $\alpha_{i,j}$ — вага уваги (attention weight), яка визначає, наскільки слово $j$ важливе для розуміння слова $i$.

В результаті:
* У лозі №1 вектор `Connection` зміщується в бік "успіху" через вплив слова `established`.
* У лозі №2 вектор `Connection` зміщується в бік "збою" через вплив слова `refused`.

## 4. Практикум: Пошук семантичних аномалій на Python

### Рекомендація

 Замість жорстких правил класифікації, використовуйте **Anomaly Detection** у векторному просторі. Якщо вектор нового логу знаходиться занадто далеко від "кластера нормальної поведінки", система має маркувати його як потенційний Unknown Unknown.

```python
from sentence_transformers import SentenceTransformer, util
import torch

# 1. Завантаження легкої моделі (SBERT), оптимізованої для пошуку схожості
model = SentenceTransformer('all-MiniLM-L6-v2')

# 2. Формування "Золотого набору" нормальної поведінки
baseline_logs = [
    "Connection established successfully",
    "User login: session initialized",
    "Request processed in 15ms",
    "Database heartbeat: OK"
]

# 3. Нові логи для діагностики
new_events = [
    "Connection established: session_id=[SESSION_ID]", # Схожий на нормальний
    "Connection refused: database unavailable",      # Критичний
    "DB link is down"                                 # Синонім критичного
]

# Обчислення ембеддінгів
baseline_embeddings = model.encode(baseline_logs, convert_to_tensor=True)
new_embeddings = model.encode(new_events, convert_to_tensor=True)

print("Аналіз семантичної схожості (Cosine Similarity):")
print("-" * 50)

for i, event in enumerate(new_events):
    # Обчислюємо максимальну схожість з базовим набором
    cosine_scores = util.cos_sim(new_embeddings[i], baseline_embeddings)
    max_score = torch.max(cosine_scores).item()
    
    status = "NORMAL" if max_score > 0.8 else "POTENTIAL ANOMALY"
    print(f"Event: {event}")
    print(f"Max Similarity: {max_score:.4f} -> Status: {status}\n")

```
**Diagnosis**: 
Повідомлення 'DB link is down' має низьку лексичну схожість з 'Connection refused', але високу семантичну відстань від 'Normal'. Це дозволяє виявляти нові типи помилок без оновлення regex.


**Hidden Risks:**
Використання сирих LLM/BERT моделей на "брудних" логах без попередньої нормалізації (Крок 0 з [02_math_setup_classification.md](../nlp_signal_noise/02_math_setup_classification.md)) призведе до того, що модель буде фокусуватися на унікальних UUID та таймстемпах, вважаючи кожен новий лог аномалією.
