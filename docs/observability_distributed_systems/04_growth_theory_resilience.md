# Теорія росту та стійкість: S-криві vs Лінійний розпад

## 1. Концепція Growth Theory у розподілених системах

**Diagnosis:** Традиційний аналіз часових рядів у моніторингу фокусується на детекції аномалій (outliers) або прогнозуванні значень (forecasting). Проте для високонавантажених мікросервісів критичним є не сам факт порушення SLA, а **динаміка накопичення порушень**. Використання **Теорії росту (Growth Theory)** дозволяє моделювати порушення продуктивності як "популяцію" дефектів, що розвивається в часі.

### Математична суть підходу
Замість аналізу миттєвої затримки (latency), ми розглядаємо кумулятивну кількість порушень вимог продуктивності $y(t)$. Стійкість системи (Resilience) визначається типом математичної моделі, яка найкраще описує цей процес:

1. **S-подібні моделі (Logistic, Gompertz):** Характерні для **стійких (Resilient)** систем. Зростання кількості порушень спочатку прискорюється, але згодом уповільнюється, наближаючись до асимптоти (ємності системи). Це свідчить про те, що механізми самовідновлення (scaling, backoff, circuit breaking) працюють.
2. **Лінійні або експоненційні моделі:** Характерні для **нестійких** систем. Порушення накопичуються без ознак стабілізації, що веде до каскадного збою.



## 2. Математичні моделі розпаду продуктивності

Для формалізації процесу використовуються нелінійні регресійні моделі. Найбільш релевантною для мікросервісів є **Логістична модель (Logistic Growth Model)**.

### Логістична модель росту порушень
Рівняння описує кумулятивні порушення $y(t)$ як функцію часу:

$$y(t) = \frac{K}{1 + e^{-r(t - t_0)}}$$

Де:
* $K$ — **Carrying Capacity**: гранична кількість порушень, яку система "дозволяє" собі до повної деградації.
* $r$ — **Growth Rate**: швидкість, з якою система втрачає продуктивність.
* $t_0$ — **Inflection Point**: точка перегину, момент максимальної швидкості деградації. Це критичний поріг для спрацювання предиктивних алертів.

### Модель Гомперца (Gompertz Model)
Використовується, коли розпад відбувається асиметрично (система деградує швидко на початку, але довго "одужує"):

$$y(t) = K \cdot e^{-b \cdot e^{-rt}}$$

**Actionable Advice:**
При аналізі метрик у Prometheus (напр. через `rate()` або кумулятивні лічильники), звертайте увагу на другу похідну графіка кумулятивних помилок. Якщо $f''(t) < 0$ (крива стає випуклою), система демонструє ознаки стійкості. Якщо $f''(t) \ge 0$, ви знаходитесь у фазі необмеженого росту дефектів — це сигнал до негайного втручання.

## 3. Предиктивне масштабування: Використання точки перегину ($t_0$)

**Diagnosis:** Традиційний Horizontal Pod Autoscaler (HPA) у Kubernetes працює реактивно: він збільшує кількість реплік лише після того, як метрика (CPU/Memory) перевищила поріг. У високонавантажених системах це призводить до запізнення (latency lag), оскільки запуск нових контейнерів потребує часу. Використання точки перегину $t_0$ з логістичної моделі дозволяє ідентифікувати момент максимального прискорення деградації ще до того, як система досягне критичного стану.

### Алгоритм предиктивного втручання:
1. **Збір вікна даних:** Накопичення кумулятивної кількості порушень SLA за останні $T$ хвилин.
2. **Апроксимація (Curve Fitting):** Використання методу найменших квадратів для знаходження параметрів $K, r, t_0$ логістичної кривої.
3. **Аналіз $t_0$:** Якщо поточний час $t$ наближається до розрахованого $t_0$, це вказує на фазу вибухового росту черги запитів або помилок.
4. **Actionable Advice:** Замість очікування порогу 80% завантаження, ініціюйте `scale-out` при виявленні точки перегину. Це забезпечує наявність ресурсів у момент пікового навантаження.

### Практична реалізація: Пошук точки перегину на Python

Нижче наведено код для апроксимації реальних даних моніторингу та визначення параметрів стійкості.

```python
import numpy as np
from scipy.optimize import curve_shift
import matplotlib.pyplot as plt

def logistic_model(t, K, r, t0):
    """Математична модель логістичного росту порушень."""
    return K / (1 + np.exp(-r * (t - t0)))

def fit_resilience_model(time_data, violation_data):
    """
    Аналіз стійкості системи через Curve Fitting.
    Повертає параметри моделі та прогнозовану точку перегину.
    """
    try:
        # Початкове наближення (p0)
        p0 = [max(violation_data), 1, np.median(time_data)]
        params, _ = curve_fit(logistic_model, time_data, violation_data, p0=p0)
        K, r, t0 = params
        
        print(f"Аналіз завершено:")
        print(f"  Capacity (K): {K:.2f} порушень")
        print(f"  Growth Rate (r): {r:.4f}")
        print(f"  Inflection Point (t0): {t0:.2f} (Index)")
        
        return params
    except Exception as e:
        print(f"Система не демонструє S-подібного (стійкого) росту: {e}")
        return None

# Синтетичні дані: кумулятивні порушення SLA (напр. latency > 500ms)
time = np.arange(0, 50, 1)
violations = logistic_model(time, 1000, 0.2, 25) + np.random.normal(0, 10, 50)

params = fit_resilience_model(time, violations)
```

## 4. Обмеження та приховані ризики (Hidden Risks)

* **Ефект "Хибного одужання"**: Модель може помилково ідентифікувати уповільнення росту (K), якщо система входить у стан "deadlock", де нові запити просто відкидаються (drop). У цьому випадку кількість порушень стабілізується не через стійкість, а через повну відмову.

* **Нестаціонарність r**: У розподілених системах швидкість деградації r може змінюватися миттєво через каскадні ефекти. Одноразовий розрахунок параметрів не є надійним; необхідне ковзне вікно аналізу (sliding window).

* **Обчислювальна складність**: Процедура curve_fit є ресурсомісткою. Не рекомендується запускати її безпосередньо в Prometheus/Grafana для кожного сервісу. Оптимальний варіант — зовнішній аналітичний компонент (AI-SRE Agent).
