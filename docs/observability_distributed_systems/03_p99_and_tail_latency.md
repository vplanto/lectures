# Математика квантилів: Чому середнє значення (Average) приховує катастрофи

## 1. Ілюзія середнього: Пастка для SRE

**Diagnosis:** У високонавантажених розподілених системах метрика "Average Latency" є токсичною, оскільки вона математично згладжує викиди (outliers), які представляють реальний біль користувачів. Коли ви бачите "середній час відповіді 200ms", ви ігноруєте той факт, що для 1% або 5% користувачів система практично не працює (затримка > 5s).

### Чому Average не працює:
* **Чутливість до розподілу:** Середнє арифметичне ($\bar{x} = \frac{1}{n} \sum x_i$) працює лише для нормального (гаусового) розподілу. Розподіл затримок у IT-системах майже завжди є **логарифмічно-нормальним** або має "важкий хвіст" (Heavy Tail).
* **Приховування мікро-інцидентів:** Якщо 999 запитів обробляються за 10ms, а 1 запит — за 10000ms (10s), середнє буде ~20ms. Виглядає як успіх, але для одного користувача це повна відмова сервісу.
* **Масштабування помилки:** У ланцюжку з 10 мікросервісів, якщо кожен має "ідеальне" середнє, але 1% запитів на кожному вузлі гальмує, то загальна ймовірність того, що кінцевий користувач відчує затримку, зростає критично (комбінаторний вибух незадоволення).



## 2. Квантилі (Percentiles) як інструмент правди

Для об'єктивної оцінки якості сервісу (SLI/SLO) використовуються квантилі (напр., P50, P95, P99).

**Визначення:** $p$-й квантиль — це таке значення, нижче якого лежить $p$ відсотків спостережень у вибірці.

### Ключові метрики для аналізу:
1. **P50 (Median):** Реальний типовий досвід користувача. 50% запитів швидші за це значення.
2. **P95:** "Поріг роздратування". 5% користувачів відчувають затримку, вищу за цю межу. Це стандарт для більшості комерційних SLA.
3. **P99:** "Межа катастрофи". Фокус на найгірших сценаріях. Якщо P99 значно відривається від P95, у вас є системна проблема в архітектурі (напр. блокуючі черги або Stop-the-world GC).

**Actionable Advice:**
При налаштуванні алертів у Grafana/Prometheus завжди дивіться на розрив (gap) між P50 та P99. Якщо P50 стабільний, а P99 росте — ви маєте справу з "отруєними запитами" (poison pills) або локальними перевантаженнями вузлів, які середнє значення ніколи не виявить.

## 3. Метрики оцінки: Чому MCC — це "Золотий стандарт" SRE

**Diagnosis:** Традиційні метрики, такі як Accuracy або F1-score, часто дають хибне відчуття безпеки при аналізі рідкісних інцидентів (High Class Imbalance). У системах моніторингу, де 99.99% подій є нормальними ($TN$ — True Negatives), модель, яка завжди каже "Все в нормі", матиме Accuracy 99.99%, але нульову діагностичну цінність.

### Проблема F1-score у моніторингу:
F1-score ігнорує $TN$ (кількість успішно оброблених запитів), фокусуючись лише на точності ($Precision$) та повноті ($Recall$) виявлення помилок. Це робить його нестійким до змін у базовій частоті подій (Base Rate), що є критичним при моделюванні стійкості систем за допомогою **Growth Theory**.

### Математика Matthews Correlation Coefficient (MCC):
Коефіцієнт кореляції Меттьюса враховує всі чотири сектори матриці помилок (Confusion Matrix). Він повертає значення від -1 до +1:
* **+1:** Ідеальне передбачення інцидентів.
* **0:** Передбачення не краще за випадкове вгадування.
* **-1:** Повна невідповідність між прогнозом та реальністю.

**Формула:**
$$MCC = \frac{TP \cdot TN - FP \cdot FN}{\sqrt{(TP + FP)(TP + FN)(TN + FP)(TN + FN)}}$$



### Реалізація оцінки моніторингу на Python

Використовуйте цей скрипт для порівняння метрик на незбалансованому датасеті логів (напр. 99% — OK, 1% — Critical).

```python
import numpy as np
from sklearn.metrics import matthews_corrcoef, f1_score, confusion_matrix

def evaluate_monitoring_quality(y_true, y_pred):
    """
    Порівняння стійкості метрик на незбалансованих даних.
    """
    mcc = matthews_corrcoef(y_true, y_pred)
    f1 = f1_score(y_true, y_pred)
    tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()
    
    accuracy = (tp + tn) / (tp + tn + fp + fn)
    
    print(f"Confusion Matrix: TP={tp}, TN={tn}, FP={fp}, FN={fn}")
    print(f"Accuracy: {accuracy:.4f} (Може бути оманливою!)")
    print(f"F1-Score: {f1:.4f}")
    print(f"MCC:      {mcc:.4f} (Золотий стандарт)")
    
    return mcc

# Сценарій: "Наївний" моніторинг, який пропускає 50% аномалій та має шум
# 10000 запитів, 100 з яких - критичні аномалії
y_true = np.array([1]*100 + [0]*9900)
y_pred = np.array([1]*50 + [0]*50 + [1]*20 + [0]*9880) # TP=50, FN=50, FP=20

evaluate_monitoring_quality(y_true, y_pred)
```

**Actionable Advice**: При розробці AI-SRE агентів використовуйте MCC як цільову функцію для оптимізації. Це гарантує, що ваша модель не просто "вгадує" нормальний стан системи, а реально розрізняє S-подібний розпад продуктивності від тимчасового шуму.
