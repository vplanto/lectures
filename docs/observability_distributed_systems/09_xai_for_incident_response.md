# Пояснювальний ШІ (XAI): Від детекції до розуміння Першопричина (Root Cause)

## 1. Проблема "Чорної скриньки": Чому інженери не вірять AI

### Факт

 Традиційні моделі Deep Learning (напр. BERT) дають результат у вигляді ймовірностей (Confidence Scores), але не пояснюють логіку прийняття рішення. У критичних ситуаціях SRE-інженер не може покладатися на "чорну скриньку", оскільки ціна помилкового рішення (напр. перезавантаження кластера БД) є занадто високою. **Explainable AI (XAI)** перетворює модель з "оракула" на прозорий інструмент діагностики.

### Ключові тенденції


* Перехід від **Post-hoc** пояснень (пояснення після факту) до **Intrinsic** моделей (прозорих за дизайном).
* Використання ігрових моделей (Cooperative Game Theory) для розподілу "провини" між вхідними ознаками (метриками/токенами логів).

## 2. Математика Shapley Values (SHAP) в SRE

### Факт

 Для розуміння, яка саме метрика або слово в лозі стали вирішальними для висновку про збій, ми використовуємо значення Шеплі.

### Формалізація внеску:
Значення Шеплі $\phi_i$ для ознаки $i$ обчислюється як середній маржинальний внесок цієї ознаки до всіх можливих комбінацій (коаліцій) інших ознак:

$$\phi_i(v) = \sum_{S \subseteq N \setminus \{i\}} \frac{|S|! (n - |S| - 1)!}{n!} [v(S \cup \{i\}) - v(S)]$$

Де:
* $v(S)$ — результат прогнозу моделі для набору ознак $S$.
* $v(S \cup \{i\}) - v(S)$ — приріст впевненості моделі при додаванні ознаки $i$.

### Рекомендація


Впровадьте SHAP-візуалізацію безпосередньо в Grafana алерти. Замість повідомлення "Critical Error", інженер має бачити: "Збій класифіковано як Network_Issue. Основні фактори: `tcp_retrans_rate` (+45%), `loki_log_token:timeout` (+30%)".

## 3. Контрфактуальний аналіз та Prescription

### Fact

 Розуміння причини ("Чому це сталося?") — це лише половина справи. Контрфактуальний аналіз (Counterfactual Explanations) відповідає на питання: "Що потрібно змінити, щоб інцидент зник?".

### Логіка "What-If":
Система шукає мінімальну зміну вхідних параметрів, яка змінить прогноз моделі з `Critical` на `Normal`.
* *Ситуація:* "Якби затримка на БД була < 200ms, каскадного збою б не було".
* *Результат (Prescription):* Автоматична генерація поради: "Масштабуйте Read-replica або перевірте блокуючі запити".

---

## 4. Hidden Risks: Ілюзія пояснення

* **Кореляція vs Причинність:** SHAP показує, на що модель *дивилася*, але це не завжди є справжньою фізичною причиною збою (Першопричина (Root Cause)).
* **Adversarial Explanations:** У складних моделях можна маніпулювати поясненнями, створюючи "красиві", але технічно некоректні обґрунтування для помилкових рішень.

---

## 5. Steelmanning

Опоненти стверджують, що обчислення Shapley Values для кожної події в High-load системі є занадто ресурсомістким (експоненційна складність $O(2^n)$). **Counter-argument:** Використання апроксимацій (KernelSHAP або TreeSHAP) дозволяє отримувати пояснення за мілісекунди, що цілком прийнятно для фази діагностики інциденту, де ціна хвилини простою перевищує витрати на обчислення.
