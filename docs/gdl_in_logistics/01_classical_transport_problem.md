## 1. Генезис оптимізації: Від Монжа до Канторовича

### 1.0. Історичний контекст: Задача Монжа (1781)

Історія сучасної логістики починається не з комп'ютерів, а з французького математика Гаспара Монжа. Під час будівництва фортець для Наполеона він сформулював задачу: як мінімізувати роботу при переміщенні землі з виїмок у насипи?

**Задача Монжа (Monge Problem):**
Нехай $\mu$ та $\nu$ — дві міри (розподіли землі) на просторах $X$ та $Y$. Потрібно знайти відображення $T: X \to Y$, яке мінімізує транспортну вартість:
$$\inf_{T_*(\mu) = \nu} \int_X c(x, T(x)) d\mu(x)$$

Де $c(x,y)$ — вартість переміщення одиниці маси з $x$ в $y$, а $T_*(\mu)$ — pushforward міри (як розподіл переміщується).

**Чому це важливо:**
Монж не мав формального апарату для вирішення, але він встановив **принцип оптимального транспорту**: оптимальне відображення не створює перехрещень (crossings). Це перша спроба формалізувати інтуїцію "найкоротший шлях".

### 1.1. Канторович та сучасна формалізація (1939-1942)

У 1939-1942 роках Леонід Канторович (СРСР) та Френк Гічкок (США) незалежно переформулювали задачу Монжа в **дискретну** форму, придатну для обчислень. Це був перехід від неперервного аналізу до лінійного програмування (Linear Programming, LP).

**Ключова ідея Канторовича:**
Замість пошуку функції $T(x)$ (що складно), шукаємо **план транспорту** $x_{ij}$ — кількість вантажу, що переміщується від $i$ до $j$. Це перетворює задачу на оптимізацію з лінійними обмеженнями.

Для нас ця задача важлива тим, що вона є "пращуром" будь-якої задачі оптимізації на графах, включаючи згортання білків (мінімізація вільної енергії).

### 1.1. Статична модель розподілу (MILP)
В основі лежить ідея оптимального переміщення однорідного вантажу від множини постачальників $S = \{S_1, \dots, S_m\}$ до споживачів $D = \{D_1, \dots, D_n\}$.
Тут простір (відстань) абстрагується у вартість (cost) переміщення одиниці ресурсу $c_{ij}$.

**Математична формалізація:**
Нехай $x_{ij}$ — кількість вантажу, що переміщується від $i$-го постачальника до $j$-го споживача.
Цільова функція (Objective Function) мінімізує сумарні витрати:

$$
Z = \min \sum_{i=1}^{m} \sum_{j=1}^{n} c_{ij} x_{ij}
$$

**Система обмежень (Constraints):**
Це класична система лінійних рівнянь, яка визначає допустиму область рішень (feasible region).

1.  **Supply Constraint (Баланс постачальника):** Ми не можемо вивезти більше, ніж є на складі $a_i$.
    $$\sum_{j=1}^{n} x_{ij} \le a_i, \quad \forall i \in \{1, \dots, m\}$$

2.  **Demand Constraint (Баланс споживача):** Попит $b_j$ має бути задоволений повністю (або, у більш м'якій постановці, не перевищений).
    $$\sum_{i=1}^{m} x_{ij} \ge b_j, \quad \forall j \in \{1, \dots, n\}$$

3.  **Non-negativity constraint (Фізична реальність):** Неможливо перевезти від'ємну кількість вантажу.
    $$x_{ij} \ge 0$$

> **Note:** Якщо $\sum a_i \neq \sum b_j$, модель стає "відкритою". Для зведення до закритої форми вводяться фіктивні вузли (dummy nodes) з $c_{dummy} = 0$. Це дозволяє використовувати симплекс-метод.

### 1.2. Симплекс-метод: Внутрішня механіка

**Чому симплекс-метод працює:**
Лінійна програма має важливу властивість: оптимальне рішення завжди лежить у **вершині** багатогранника допустимих рішень (feasible polyhedron). Симплекс-метод "ковзає" по ребрах цього багатогранника від вершини до вершини, поки не досягне оптимуму.

**Алгоритм (спрощено):**
1. Починаємо з базисного допустимого рішення (BFS)
2. Обчислюємо **reduced costs**: $\bar{c}_{ij} = c_{ij} - u_i - v_j$
3. Якщо всі $\bar{c}_{ij} \ge 0$ → оптимальне рішення знайдено
4. Інакше: обираємо ребро з $\bar{c}_{ij} < 0$ та "входимо" в нову вершину (pivot operation)
5. Повторюємо до збіжності

**Складність:**
- Найгірший випадок: $O(2^n)$ ітерацій (експоненціально)
- На практиці: $O(m + n)$ ітерацій (поліноміально для більшості випадків)
- Чому це працює: геометрія багатогранника "добре поводиться" для реальних задач

**Проблема масштабування:**
Для задачі з $m=1000$ постачальників та $n=1000$ споживачів матриця обмежень має розмір $2000 \times 1,000,000$. Кожна ітерація симплексу потребує обернення підматриці розміру $2000 \times 2000$ — це $O(2000^3) = 8$ мільярдів операцій. Навіть на сучасному CPU це займає секунди.

> **📚 Детальний аналіз:** Детальний аналіз впливу розмірності на методи Monte Carlo та Grid Search див. у розділі [02_algorithm_limitations.md](./02_algorithm_limitations.md).

### 1.3. Метод потенціалів та Двоїстість (Duality)

Класичний метод розв'язання транспортної задачі (MODI — Modified Distribution Method) базується на теорії двоїстості Лагранжа. Це критично важливо для розуміння сучасних нейромереж, оскільки backpropagation по суті вирішує задачу мінімізації помилки схожим чином.

**Двоїста задача (Dual Problem):**
Максимізувати:
$$\max \sum_{i=1}^{m} a_i u_i + \sum_{j=1}^{n} b_j v_j$$

За обмеженнями:
$$u_i + v_j \le c_{ij}, \quad \forall i,j$$

**Теорема про двоїстість (Duality Theorem):**
Якщо існує оптимальне рішення прямої задачі, то існує оптимальне рішення двоїстої, і значення цільових функцій збігаються:
$$\min Z = \max \left(\sum_{i=1}^{m} a_i u_i + \sum_{j=1}^{n} b_j v_j\right)$$

**Умова доповняльної нежорсткості (Complementary Slackness):**
Для оптимального рішення:
- Якщо $x_{ij} > 0$ (активний маршрут), то $u_i + v_j = c_{ij}$ (рівність)
- Якщо $u_i + v_j < c_{ij}$ (неактивний маршрут), то $x_{ij} = 0$

Кожному вузлу присвоюється потенціал: $u_i$ (для джерела) та $v_j$ (для стоку).
Для будь-якого активного маршруту ($x_{ij} > 0$) має виконуватись умова рівноваги:
$$u_i + v_j = c_{ij}$$

Економічний зміст: $u_i$ та $v_j$ — це "тіньові ціни" (shadow prices). Якщо для якогось порожнього маршруту виявляється, що $u_i + v_j > c_{ij}$, це сигнал для алгоритму: "використання цього ребра зменшить глобальну вартість". Це аналог градієнта в ML.

**Чому це швидше за симплекс:**
MODI працює безпосередньо з транспортною таблицею, уникаючи повної матриці обмежень. Складність: $O((m+n)^2)$ замість $O((m+n)^3)$ для симплексу.

## 2. Еволюція в TSP: Від потоків до послідовностей

Транспортна задача розподіляє *об'єми*. Але логістика часто вимагає *послідовності*. Як тільки ми ставимо питання "в якому порядку відвідати точки", ми переходимо до **Traveling Salesman Problem (TSP)**.

Це фундаментальний стрибок складності: від поліноміальної задачі LP ми переходимо до комбінаторної задачі на пермутаціях.

### 2.1. Формалізація MTZ (Miller-Tucker-Zemlin)

Чому TSP складно записати мовою математики? Проблема в **subtours** (підциклах). Якщо просто вимагати, щоб у кожне місто входили й виходили по одному разу, розв'язувач може видати два незалежних кільця замість одного великого маршруту.

**Приклад subtour:**
Для 6 міст розв'язувач може знайти: $1 \to 2 \to 3 \to 1$ та $4 \to 5 \to 6 \to 4$ — два окремі цикли замість одного $1 \to 2 \to 3 \to 4 \to 5 \to 6 \to 1$.

**Рішення MTZ (1960):**
Для заборони підциклів вводять змінні порядку $u_i \in \{2, 3, \dots, n\}$ (крок, на якому відвідується місто $i$). Місто 1 (депо) має $u_1 = 1$.

Обмеження MTZ виглядає так:
$$u_i - u_j + n \cdot x_{ij} \le n - 1, \quad \forall 2 \le i \neq j \le n$$

Де $x_{ij} \in \{0, 1\}$ — бінарна змінна (їдемо чи ні).

**Доведення, чому це працює:**

Припустимо, що існує subtour, який не містить депо (місто 1). Нехай це цикл $i_1 \to i_2 \to \dots \to i_k \to i_1$, де $i_1, \dots, i_k \ge 2$.

Для кожного ребра $(i_j, i_{j+1})$ в циклі маємо $x_{i_j i_{j+1}} = 1$, тому:
$$u_{i_j} - u_{i_{j+1}} + n \le n - 1$$
$$u_{i_j} - u_{i_{j+1}} \le -1$$

Сума по всьому циклу:
$$\sum_{j=1}^{k} (u_{i_j} - u_{i_{j+1}}) = (u_{i_1} - u_{i_2}) + (u_{i_2} - u_{i_3}) + \dots + (u_{i_k} - u_{i_1}) = 0$$

Але з обмежень MTZ: $\sum_{j=1}^{k} (u_{i_j} - u_{i_{j+1}}) \le -k < 0$ — протиріччя!

**Висновок:** Будь-який цикл, який не містить депо, порушує обмеження MTZ. Тому оптимальне рішення має лише один цикл, який проходить через всі міста.

**Ціна складності:**
Це обмеження гарантує зв'язність графа, але ціною введення $O(n^2)$ додаткових обмежень та $O(n)$ додаткових змінних. Саме це робить точне вирішення TSP вкрай важким для класичних солверів (Gurobi, CPLEX) при $N > 100$.

**Альтернатива: Subtour Elimination Constraints (SEC)**
Замість $O(n^2)$ обмежень MTZ можна використати експоненційну кількість обмежень:
$$\sum_{i \in S} \sum_{j \notin S} x_{ij} \ge 2, \quad \forall S \subset \{2, \dots, n\}, |S| \ge 2$$

Це $2^{n-1} - n$ обмежень, але на практиці додаються лише ті, які порушуються (lazy constraints). Для $n=100$ це мільйони обмежень, але солвер додає лише десятки на ітерацію.

## 3. NP-повні задачі та межі обчислюваності

Інженер повинен розуміти природу NP-повноти не як абстракцію, а як стіну, об яку розбиваються наївні алгоритми.

### 3.1. Визначення через редукцію
TSP є **NP-hard**. Це означає:
1.  Не існує відомого алгоритму, який вирішує її за поліноміальний час $O(n^k)$.
2.  Будь-яка інша задача з класу NP (наприклад, фолдинг білка) може бути зведена (reduced) до TSP за поліноміальний час.

**Практичний висновок:** Якщо ви навчитесь ефективно вирішувати TSP (або VRP) за допомогою нейромережі (як AlphaFold 2), ви фактично створите універсальний солвер для широкого класу задач, від розкладу процесора до дизайну ліків.

### 3.2. Комбінаторний вибух
Кількість можливих маршрутів для $N$ міст у симетричному TSP дорівнює:
$$\frac{(N-1)!}{2}$$

* $N=10$: $181,440$ варіантів (мікросекунди).
* $N=20$: $\approx 6 \times 10^{16}$ варіантів (роки роботи CPU без відсікань).
* $N=60$: Кількість варіантів перевищує кількість атомів у Всесвіті.

Саме тому "груба сила" (Brute Force) мертва. Нам потрібні алгоритми, які "відчувають" структуру простору, а не перебирають її.

## 4. Алгоритмічний ландшафт: Від точності до евристик

### 4.1. Точні методи (Exact Methods)

Вони гарантують **глобальний оптимум**, але не масштабуються.

#### 4.1.1. Held-Karp Algorithm (1962): Dynamic Programming для TSP

**Ідея:** Замість перебору всіх $O(N!)$ маршрутів, зберігаємо оптимальну вартість для підмножин міст.

**Формалізація:**
Нехай $C(S, j)$ — мінімальна вартість відвідати всі міста з множини $S$, закінчуючи в місті $j$, де $S \subseteq \{1, \dots, n\}$ та $1 \in S$ (депо завжди включено).

**Рекурентне співвідношення:**
$$C(S, j) = \begin{cases}
0 & \text{якщо } S = \{1\} \text{ та } j = 1 \\
\min_{i \in S \setminus \{j\}} [C(S \setminus \{j\}, i) + c_{ij}] & \text{інакше}
\end{cases}$$

**Оптимальна вартість:**
$$OPT = \min_{j=2}^{n} [C(\{1, \dots, n\}, j) + c_{j1}]$$

**Складність:**
- Кількість підмножин: $2^{n-1}$ (депо завжди включено)
- Для кожної підмножини: $O(n)$ міст для перевірки
- Загальна складність: $O(n^2 \cdot 2^n)$

**Пам'ять:**
Таблиця $C(S, j)$ потребує $O(n \cdot 2^n)$ пам'яті. Для $n=30$: $30 \times 2^{29} \approx 16$ мільярдів записів × 8 байт = 128 GB RAM.

**Практичні межі:**
- $n \le 20$: секунди на CPU
- $n \le 25$: хвилини на CPU
- $n \le 30$: години на CPU з оптимізаціями (bitmask, мемоізація)
- $n > 30$: непрактично через пам'ять

**Чому це краще за brute force:**
Brute force: $O(n!)$ операцій. Для $n=20$: $20! \approx 2.4 \times 10^{18}$.
Held-Karp: $O(n^2 \cdot 2^n)$. Для $n=20$: $20^2 \times 2^{20} \approx 4 \times 10^8$ — в 6 мільярдів разів швидше.

#### 4.1.2. Branch and Bound (Гілки та Межі): Внутрішня механіка

**Ідея:** Розбиваємо простір рішень на дерево підзадач. Якщо оцінка нижньої межі (Lower Bound) гілки гірша за поточний рекорд (Upper Bound), вся гілка відсікається (pruning).

**Алгоритм:**
1. **Ініціалізація:** Обчислюємо початкову верхню межу (Upper Bound) — наприклад, жадібним алгоритмом або 2-Opt.
2. **Розгалуження (Branching):** Обираємо ребро $(i,j)$ та створюємо дві гілки:
   - Гілка 1: $x_{ij} = 1$ (ребро включено в маршрут)
   - Гілка 2: $x_{ij} = 0$ (ребро виключено)
3. **Обмеження (Bound):** Для кожної гілки обчислюємо нижню межу (Lower Bound):
   - **1-Tree Lower Bound:** Видаляємо одне місто, будуємо мінімальне остовне дерево (MST) для решти, додаємо два найкоротші ребра до видаленого міста.
   - **Held-Karp Lower Bound:** Використовуємо релаксацію лінійного програмування.
4. **Відсікання (Pruning):** Якщо $LB \ge UB$, гілка відсікається.
5. **Оновлення:** Якщо знайдено краще рішення, оновлюємо $UB$.
6. **Повторюємо** до тих пір, поки всі гілки не відсічені або не перевірені.

**Приклад обчислення Lower Bound (1-Tree):**

Для TSP з 5 містами:
- Видаляємо місто 1 (депо)
- Будуємо MST для міст {2,3,4,5}: наприклад, $2-3-4-5$ з вагою $w_{MST} = 10$
- Додаємо два найкоротші ребра до міста 1: $\min(c_{12}, c_{13}, c_{14}, c_{15}) + \text{другий мінімум} = 3 + 4 = 7$
- **Lower Bound:** $LB = 10 + 7 = 17$

Це гарантовано менше або дорівнює оптимальній вартості, бо будь-який гамильтонів цикл містить остовне дерево плюс два ребра до депо.

**Складність:**
- Найгірший випадок: $O(2^n)$ гілок (експоненціально)
- На практиці: ефективне відсікання зменшує кількість гілок у $10^3 - 10^6$ разів
- Для $n=50$: зазвичай перевіряється $10^6 - 10^9$ гілок замість $2^{50} \approx 10^{15}$

**Проблема пам'яті:**
Кожна гілка потребує зберігання стану (часткове рішення, bounds, constraints). Для $n=100$ це може бути $>10^9$ активних гілок одночасно — це $>1$ TB RAM.

> **📚 Фізичні обмеження:** Про фізичні обмеження адресного простору 64-бітних систем при побудові дерев пошуку див. технічний розбір у модулі [00_geometric_deep_learning_intro.md](./00_geometric_deep_learning_intro.md).

**Висновок:** Branch & Bound ефективний для $n \le 60-80$ з потужними серверами. Для більших задач потрібні евристики або Deep Learning.

### 4.2. Жадібні алгоритми (Greedy)

#### 4.2.1. Nearest Neighbor (Найближчий сусід)

**Логіка:** Завжди йди до найближчого невідвіданого міста.

**Псевдокод:**
```python
def nearest_neighbor_tsp(cities, start=0):
    tour = [start]
    unvisited = set(range(len(cities))) - {start}
    current = start
    
    while unvisited:
        nearest = min(unvisited, key=lambda j: distance(cities[current], cities[j]))
        tour.append(nearest)
        unvisited.remove(nearest)
        current = nearest
    
    tour.append(start)  # Повернення в депо
    return tour
```

**Складність:** $O(N^2)$ — для кожного з $N$ міст перевіряємо $O(N)$ сусідів.

**Проблема:** "Жадібність" сліпа до горизонту. Останній перехід (повернення в депо) часто буває катастрофічно довгим.

**Приклад помилки:**
```
Міста: A(0,0), B(1,0), C(2,0), D(10,0)
Оптимальний маршрут: A→B→C→D→A = 1+1+8+10 = 20
Nearest Neighbor: A→B→C→D→A = 1+1+8+10 = 20 (випадково оптимально)

Але якщо додати E(5,10):
Оптимальний: A→B→C→D→E→A ≈ 1+1+8+√(64+100)+√(25+100) ≈ 30
Nearest Neighbor: A→B→C→D→E→A = 1+1+8+√(64+100)+√(100+100) ≈ 35 (17% помилка)
```

**Теоретична оцінка помилки:**
Для евклідового TSP на площині Nearest Neighbor має апроксимаційний коефіцієнт:
$$\frac{C_{NN}}{C_{OPT}} \le \frac{1}{2}(\lceil \log_2 n \rceil + 1)$$

Для $n=100$: помилка може сягати $50 \times \log_2(100) \approx 350\%$ у найгіршому випадку. На практиці: 20-30% для випадкових розподілів.

#### 4.2.2. Assignment Problem: Спеціальний випадок

**Постановка:** Потрібно призначити $n$ робітників на $n$ завдань так, щоб мінімізувати сумарну вартість. Це **не** TSP, бо не вимагає циклу.

**Математична формалізація:**
$$\min \sum_{i=1}^{n} \sum_{j=1}^{n} c_{ij} x_{ij}$$

За обмеженнями:
- $\sum_{j=1}^{n} x_{ij} = 1$ (кожен робітник призначається на одне завдання)
- $\sum_{i=1}^{n} x_{ij} = 1$ (кожне завдання виконується одним робітником)
- $x_{ij} \in \{0, 1\}$

**Відмінність від TSP:**
Assignment Problem — це **біпартитний граф** (робітники ↔ завдання), тоді як TSP — це **повний граф** (всі міста з'єднані між собою).

**Алгоритм: Угорський метод (Hungarian Algorithm)**
Складність: $O(n^3)$ — поліноміально! Це один з небагатьох випадків, коли задача призначення вирішується точно за поліноміальний час.

**Зв'язок з TSP:**
Якщо Assignment Problem розв'язати для TSP (ігноруючи обмеження циклу), отримаємо нижню межу для TSP. Це використовується в Branch & Bound.

### 4.3. Локальний пошук (k-Opt)

Методи покращення існуючого рішення через локальні зміни.

#### 4.3.1. 2-Opt: Видалення перехресть

**Ідея:** Якщо два ребра маршруту перетинаються, їх можна замінити на два інші ребра без перетину, зменшивши загальну довжину.

**Алгоритм:**
1. Обираємо два ребра $(i, i+1)$ та $(j, j+1)$ з поточного маршруту
2. Перевіряємо: чи $c_{i,i+1} + c_{j,j+1} > c_{i,j} + c_{i+1,j+1}$?
3. Якщо так: замінюємо ребра та "перевертаємо" сегмент між $i+1$ та $j$

**Візуалізація:**
```
До:  ... → i → i+1 → ... → j → j+1 → ...
Після: ... → i → j → ... → i+1 → j+1 → ...
```

**Складність одного кроку:** $O(n^2)$ — перевіряємо всі пари ребер.
**Складність до збіжності:** $O(n^2 \cdot k)$, де $k$ — кількість ітерацій (зазвичай $k = O(n)$).

**Проблема:** Може застрягнути в локальному мінімумі. Для виходу використовують **3-Opt** або **Lin-Kernighan**.

#### 4.3.2. 3-Opt: Перестановка сегментів

**Ідея:** Видаляємо три ребра та переставляємо три сегменти маршруту у всіх можливих комбінаціях.

**Кількість варіантів:** Для трьох сегментів існує 7 способів їх з'єднати (включаючи оригінальний).

**Складність:** $O(n^3)$ на крок, але краща якість рішення.

**Практичне застосування:**
2-Opt та 3-Opt використовуються як **полірування** (polishing) після отримання початкового рішення (наприклад, від нейромережі). Це дозволяє покращити результат на 5-10% за додаткові $O(n^2)$ операцій.

#### 4.3.3. Енергетичний ландшафт та локальні мінімуми

Це ітеративний процес спуску по **енергетичному ландшафту** (energy landscape) до локального мінімуму. 

**Візуалізація ландшафту:**
Уявіть поверхню з пагорбами та долинами. Кожна точка — це маршрут, висота — це вартість маршруту. 2-Opt/3-Opt "котиться вниз" до найближчої долини, але може не знайти найглибшу долину (глобальний мінімум).

**Кількість локальних мінімумів:**
Для випадкового TSP з $n$ містами очікувана кількість локальних мінімумів 2-Opt експоненційно залежить від $n$:
$$E[\text{# локальних мінімумів}] \approx O(2^{n/2})$$

Для $n=50$: мільйони локальних мінімумів. Навіть запуск 2-Opt з тисячами різних початкових точок не гарантує знаходження глобального оптимуму.

**Висновок:** Локальний пошук швидкий ($O(n^2)$), але не надійний. Потрібні методи, які "стрибають" через бар'єри між долинами — саме це робить Deep Learning через attention mechanism.

## 5. Vehicle Routing Problem (VRP): Реальний світ

VRP узагальнює TSP на випадок $K$ транспортних засобів. Тут матриця вартості $C$ доповнюється тензорами обмежень.

### 5.1. CVRP (Capacitated VRP) & Fuel Constraints
Додаємо фізику.
* **Capacity:** $\sum q_i \le Q_{vehicle}$ для кожного маршруту.
* **Fuel/Distance:** Довжина маршруту $L_k \le L_{max}$.
У моделях електромобілів (EVRP) вартість дуги $c_{ij}$ стає динамічною: вона залежить від завантаження машини (маса впливає на розхід) та рельєфу.

### 5.2. VRPTW (Time Windows)
Найжорсткіше обмеження. Клієнт $i$ приймає лише в інтервалі $[e_i, l_i]$.
Прибуття раніше $e_i$ призводить до простою (wait time penalty). Прибуття пізніше $l_i$ — неможливе (hard constraint).
Це перетворює задачу з геометричної на просторово-часову. Граф стає орієнтованим у часі.

## 6. Імплементація та Обчислювальна архітектура

Ефективність алгоритму залежить не лише від математики, а й від того, як ми зберігаємо дані в пам'яті та як обираємо напрямок пошуку.

### 6.1. Проблема "Порожнього простору" (Matrix vs CSR)

У реальній логістиці графи **розріджені (sparse)**. З одного перехрестя можна поїхати лише у 3-4 напрямках, а не у всі 10,000 міст одночасно.

**Математичне визначення розрідженості:**
Граф з $n$ вершинами та $m$ ребрами називається розрідженим, якщо $m \ll n^2$. Для дорожнього графа: $m \approx 3n$ (кожен перехрест з'єднаний з 3-4 сусідами в середньому).

**Коефіцієнт розрідженості:**
$$\text{Sparsity} = 1 - \frac{m}{n^2}$$

Для $n=10,000$ та $m=30,000$: Sparsity = $1 - 30,000/100,000,000 = 99.97\%$ — матриця на 99.97% складається з нулів.

**Візуалізація проблеми пам'яті:**

**А. Adjacency Matrix (Матриця суміжності):**
Зберігає ВСІ можливі зв'язки. Якщо зв'язку немає — зберігає `0` (або `Inf`).
* $N=4$ міста. Пам'ять заповнена "сміттям" (нулями).

|   | A | B | C | D |
|---|---|---|---|---|
| **A** | 0 | **5** | 0 | 0 |
| **B** | 0 | 0 | **2** | 0 |
| **C** | 0 | 0 | 0 | **8** |
| **D** | **1** | 0 | 0 | 0 |

*(Для карти України це буде таблиця 30,000 × 30,000, яка на 99.9% складається з нулів. Це ~7 ГБ RAM лише для зберігання "порожнечі".)*

**Пам'ять:** $O(n^2)$ незалежно від кількості ребер.

**Б. Compressed Sparse Row (CSR) / Adjacency List:**
Ми зберігаємо **тільки існуючі** зв'язки. Це вектори, де індекс вказує на зміщення.

```text
Values:  [5, 2, 8, 1]       <-- Тільки реальні ваги (вартість проїзду)
Columns: [1, 2, 3, 0]       <-- Куди веде ребро (ID міста)
RowPtr:  [0, 1, 2, 3, 4]    <-- Індекси, де починаються сусіди для кожного вузла
```

**Пам'ять:** $O(n + m)$ — лінійна за кількістю вершин та ребер.

**Порівняння для $n=30,000$, $m=90,000$:**
- Dense Matrix: $30,000^2 \times 8$ байт = 7.2 GB
- CSR: $(30,000 + 90,000) \times 8$ байт = 960 KB
- **Економія: 7,500×**

**В. Coordinate Format (COO):**
Зберігає список трійок $(i, j, w_{ij})$ для кожного ребра.

```text
Row indices:    [0, 1, 2, 3]
Column indices: [1, 2, 3, 0]
Values:         [5, 2, 8, 1]
```

**Переваги:** Легко додавати/видаляти ребра (додати/видалити елемент у списку).
**Недоліки:** Повільніше для матричних операцій (потрібна конвертація в CSR).

**В. Compressed Sparse Column (CSC):**
Аналогічно CSR, але стиснення по стовпцях замість рядків. Корисно для операцій типу $A^T \cdot v$.

**Обчислювальна складність операцій:**

| Операція | Dense | CSR | COO |
|----------|-------|-----|-----|
| $A \cdot v$ (matrix-vector) | $O(n^2)$ | $O(m)$ | $O(m)$ (після конвертації) |
| Доступ до $A_{ij}$ | $O(1)$ | $O(\text{deg}(i))$ | $O(m)$ |
| Додавання ребра | $O(1)$ | $O(1)$ амортизовано | $O(1)$ |
| Пам'ять | $O(n^2)$ | $O(n+m)$ | $O(m)$ |

**Висновок:** Для ML-моделей (Graph Neural Networks) та солверів ми завжди використовуємо **CSR**. Це критично для швидкості множення матриць на GPU (cuSPARSE оптимізований саме для CSR).

### 6.2. Роль Евристики: Як додати "інтуїцію" в алгоритм
Щоб зрозуміти, навіщо нам Deep Learning у логістиці, треба зрозуміти різницю між "сліпим" та "спрямованим" пошуком.

1.  **Сліпий пошук (Dijkstra):**
    Уявіть, що ви в темній кімнаті шукаєте вихід. Ви мацаєте всі стіни навколо себе рівномірно. Алгоритм перевіряє всі можливі шляхи на всі боки, поки не наткнеться на ціль. Це надійно (знайде ідеальний шлях), але дуже повільно, бо ви досліджуєте тисячі непотрібних напрямків.

2.  **Спрямований пошук:**
    У вас з'явився компас (евристика). Ви не перевіряєте всі стіни, а йдете переважно в бік "півночі", бо знаєте, що ціль там. Ви економите ресурси, ігноруючи шляхи, що ведуть у протилежний бік.

**Проблема класичного компаса:**
У звичайній логістиці "компас" працює примітивно — він міряє відстань по прямій лінії (як птах летить). Але на землі є річки, гори та затори. "Пряма лінія" каже йти прямо, а там прірва. Через це алгоритм помиляється і все одно витрачає час.

**Рішення через AI (Deep Learning):**
Нейромережі дозволяють створити **"Розумний компас"**. Замість вимірювання лінійкою по карті, модель аналізує тисячі факторів (рельєф, історію, затори) і каже: *"Хоч ціль на півночі, тобі треба спочатку на схід, бо там міст"*.
Тобто, Deep Learning тут виступає як ідеальна інтуїція, що перетворює перебір варіантів на майже миттєве знаходження маршруту.

### 6.3. Алгоритм A* (A-Star): Фундамент навігації
Перед тим як вирішувати задачу комівояжера (VRP), нам потрібно знати точну відстань між кожною парою точок. Цю задачу вирішує A*.

**Суть алгоритму:**
Це модифікація алгоритму Дейкстри, яка використовує "передбачення" (евристику) для прискорення пошуку. Він обирає шлях, мінімізуючи функцію:
$$f(n) = g(n) + h(n)$$

* **$g(n)$ (Cost so far):** Реальна вартість шляху від старту до поточної точки $n$.
* **$h(n)$ (Heuristic):** Оцінка відстані від $n$ до фінішу (наприклад, пряма лінія).

**Роль у нашому курсі:**
1.  **Data Preparation:** Ми запускаємо A* тисячі разів на дорожньому графі (OSRM), щоб побудувати Матрицю Вартостей ($C_{ij}$), яку потім "згодовуємо" моделям VRP або AlphaFold.
2.  **Концептуальний міст:** $h(n)$ — це перша спроба в історії алгоритмів використати "передбачення" замість перебору. У Deep Learning ми просто замінюємо просту формулу $h(n)$ на складну нейромережу.

## 7. Порівняльна таблиця алгоритмів: Складність та практичні межі

### 7.1. Таблиця порівняння

| Алгоритм | Складність (час) | Складність (пам'ять) | Практична межа ($n$) | Гарантія оптимальності | Примітки |
|----------|------------------|----------------------|---------------------|----------------------|----------|
| **Brute Force** | $O(n!)$ | $O(1)$ | $n \le 10$ | ✅ Глобальний оптимум | Тільки для навчальних цілей |
| **Held-Karp (DP)** | $O(n^2 \cdot 2^n)$ | $O(n \cdot 2^n)$ | $n \le 30$ | ✅ Глобальний оптимум | Експоненційна пам'ять |
| **Branch & Bound** | $O(2^n)$ найгірший | $O(2^n)$ найгірший | $n \le 60-80$ | ✅ Глобальний оптимум | Залежить від якості bounds |
| **Nearest Neighbor** | $O(n^2)$ | $O(n)$ | $n \le 10^6$ | ❌ 20-30% помилка | Швидкий, але неточний |
| **2-Opt** | $O(n^2 \cdot k)$ | $O(n)$ | $n \le 10^4$ | ❌ Локальний мінімум | Полірування рішення |
| **3-Opt** | $O(n^3 \cdot k)$ | $O(n)$ | $n \le 10^3$ | ❌ Локальний мінімум | Краща якість за 2-Opt |
| **Lin-Kernighan** | $O(n^{2.2})$ | $O(n)$ | $n \le 10^5$ | ❌ Локальний мінімум | Найкраща евристика |
| **GDL/AlphaFold** | $O(n^2 \cdot L)$ | $O(n^2)$ | $n \le 10^6$ | ❌ 1-5% помилка | Потрібен GPU, навчання |

Де $k$ — кількість ітерацій до збіжності (зазвичай $k = O(n)$), $L$ — кількість шарів нейромережі.

### 7.2. Вибір алгоритму за розміром задачі

**$n \le 20$:** Використовуємо **Held-Karp** або **Branch & Bound**. Гарантований оптимум за секунди.

**$20 < n \le 100$:** **Branch & Bound** з потужним сервером (64+ GB RAM). Може зайняти хвилини-години.

**$100 < n \le 1000$:** **Lin-Kernighan** або **3-Opt** з багатьма запусками з різних початкових точок. Точність: 1-3% від оптимуму.

**$n > 1000$:** **Geometric Deep Learning** (AlphaFold-подібна архітектура). Єдина опція для real-time обробки мільйонів запитів.

**Критерії оцінки:**
- **Недостатньо:** "Використаємо Gurobi, бо він точний" (немає аналізу latency/throughput)
- **Добре:** Розрахунок throughput/latency з конкретними числами та обґрунтування вибору
- **Відмінно:** Аналіз trade-offs, масштабованість, обґрунтування через метрики (не інтуїцію), врахування часових вікон та обмежень вантажопідйомності

### 8.2. Референсне рішення (для викладача)

**Рекомендована архітектура: B) Hybrid (GDL + 2-Opt)**

**Обґрунтування:**

**Етап 1: GDL Model (GPU)**
- Модель: 6 шарів MPNN + Attention, $d=128$
- Batch size: 64 instances per GPU
- Throughput: 4 GPU × 64 instances/GPU × 10 batches/sec = 2,560 instances/sec
- Latency: $P_{50}=80$ ms, $P_{99}=150$ ms
- Точність: 5-8% від оптимуму (до полірування)

**Етап 2: 2-Opt Polishing (CPU)**
- Застосовується до топ-20% найскладніших випадків (визначено через еврістику: $n > 15$ або tight time windows)
- Складність: $O(n^2)$ на instance
- Throughput: 32 CPU cores × 4 сервери = 128 cores, кожен обробляє 1 instance за ~50 ms → 2,560 instances/sec
- Покращення: зменшує помилку з 5-8% до 2-3%

**Загальна система:**
- **Throughput:** 2,560 instances/sec (обмежено GPU, CPU має запас)
- **Latency:** $P_{50}=130$ ms, $P_{99}=200$ ms (в межах вимог $<500$ ms)
- **Точність:** 2-3% від оптимуму (в межах вимог $<3\%$)
- **Вартість:** 4× A100 GPU + 128 CPU cores, енергоспоживання ~8 kW

**Порівняння з альтернативами:**

**A) Gurobi B&B:**
- Throughput: ~10 instances/sec (занадто повільно)
- Latency: $P_{99} > 5$ секунд (порушує вимоги)
- ❌ Не підходить для real-time

**C) Повністю GDL:**
- Throughput: 2,560 instances/sec (аналогічно)
- Latency: $P_{99}=150$ ms (краще)
- Точність: 5-8% (гірше за вимоги)
- ❌ Не відповідає вимогам точності

**Масштабування:**
Для 10,000 RPS потрібно додати 3 сервери (тепер 7 серверів, 7× A100, 224 CPU cores). Система масштабується лінійно.
