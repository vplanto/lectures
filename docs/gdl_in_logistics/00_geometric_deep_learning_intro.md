## 1. Проблема масштабування: Чому класичні алгоритми вмирають

### 1.1. Реальний тригер: Падіння системи маршрутизації на Black Friday

У 2021 році одна з найбільших e-commerce платформ України зіткнулася з катастрофою: система планування доставки перестала відповідати під час пікового навантаження. Замість 5-10 секунд на генерацію маршрутів для 200 кур'єрів, система зависала на 2-3 хвилини, або взагалі падала з помилкою `OutOfMemoryError`.

**Технічний розбір:**
- **Класичний підхід:** Branch & Bound (Gurobi Optimizer) на CPU
- **Розмір задачі:** 200 клієнтів, 50 транспортних засобів, 3D координати + часові вікна
- **Складність:** $O(2^{200})$ у найгіршому випадку
- **Пам'ять:** Матриця відстаней $200 \times 200 = 40,000$ елементів × 8 байт = 320 KB (не проблема)
- **Реальна проблема:** Дерево пошуку Branch & Bound створює $10^9+$ вузлів, кожен з яких потребує ~1 KB для зберігання стану (bounds, constraints). Це $>1$ TB RAM.

**Фізичне обмеження:**
Навіть на сервері з 512 GB RAM, операційна система не може виділити більше 256 GB для одного процесу (обмеження адресного простору в 64-бітних системах). Алгоритм вмирає не через математику, а через архітектуру пам'яті.

### 1.2. Прокляття розмірності (Curse of Dimensionality)

Класичні алгоритми оптимізації (симплекс-метод, B&B) працюють у **евклідовому просторі** з фіксованою розмірністю. Але логістична задача — це не просто координати $(x, y)$.

**Повний простір станів для VRP:**
- Географічні координати: 2D або 3D
- Час прибуття: 1D
- Залишок палива/зарядки: 1D
- Завантаження вантажу: 1D
- Історія відвіданих вузлів: $N$ бітів (one-hot encoding)

**Загальна розмірність:** $d = 2 + 1 + 1 + 1 + N = N + 5$

Для $N=200$ клієнтів це простір розмірності $d=205$. Кількість точок, необхідних для рівномірного покриття гіперкуба $[0,1]^{205}$, дорівнює $k^{205}$, де $k$ — кількість точок на кожну вісь. Навіть для $k=2$ це $2^{205} \approx 10^{61}$ точок.

**Висновок:** Жоден дискретний алгоритм не може перебрати цей простір. Потрібен **неперервний** підхід, який "відчуває" структуру простору, а не перераховує його.

## 2. Геометричний Deep Learning: Математичний фундамент

### 2.1. Визначення через теорію груп

**Геометричний Deep Learning (GDL)** — це клас архітектур нейромереж, які зберігають **інваріантність** щодо перетворень симетрії простору.

**Формальне визначення:**
Нехай $G$ — група перетворень (наприклад, обертання, відбиття, переноси). Функція $f: X \to Y$ називається **$G$-інваріантною**, якщо:
$$f(g \cdot x) = f(x), \quad \forall g \in G, x \in X$$

**Приклад для логістики:**
Якщо ми обертаємо всю карту міст навколо депо на $90°$, оптимальний маршрут має залишитися оптимальним (з точністю до обертання координат). Класична нейромережа (MLP) цього не гарантує — вона навчиться конкретній орієнтації. GDL-архітектура автоматично інваріантна.

### 2.2. Граф як геометричний об'єкт

**Ключова ідея:** Міста та дороги — це не просто точки та лінії. Це **граф** з геометричною структурою.

**Математична модель:**
Граф $G = (V, E)$ де:
- $V = \{v_1, \dots, v_N\}$ — множина вершин (міста, клієнти)
- $E \subseteq V \times V$ — множина ребер (дороги, можливі переміщення)
- Кожна вершина має **features** $h_i \in \mathbb{R}^d$ (координати, попит, часові вікна)
- Кожне ребро має **edge features** $e_{ij} \in \mathbb{R}^k$ (відстань, час проїзду, вартість)

**Геометрична структура:**
Відстань між вершинами $v_i$ та $v_j$ визначається не лише евклідовою метрикою $\|x_i - x_j\|_2$, але й **графовою метрикою** (shortest path distance):
$$d_G(v_i, v_j) = \min_{p \in \text{paths}(i,j)} \sum_{(u,v) \in p} w_{uv}$$

Де $w_{uv}$ — вага ребра (час, вартість, відстань).

### 2.3. Message Passing: Як нейромережа "бачить" граф

**Класична нейромережа (MLP)** приймає на вхід фіксований вектор $x \in \mathbb{R}^n$. Але граф має **змінну структуру** — кількість сусідів у кожної вершини різна.

**Рішення: Message Passing Neural Network (MPNN):**

На кожному шарі $l$ вершина $v_i$ отримує "повідомлення" від сусідів та оновлює своє представлення:

$$h_i^{(l+1)} = \text{UPDATE}^{(l)}\left(h_i^{(l)}, \text{AGGREGATE}^{(l)}\left(\{h_j^{(l)} : j \in \mathcal{N}(i)\}\right)\right)$$

Де:
- $\mathcal{N}(i)$ — множина сусідів вершини $i$
- $\text{AGGREGATE}$ — функція агрегації (сума, середнє, максимум)
- $\text{UPDATE}$ — нейромережа (MLP), яка оновлює features

**Чому це працює:**
Після $L$ шарів, вершина $v_i$ "бачить" всі вершини на відстані $\le L$ (receptive field). Для задачі маршрутизації це означає, що модель враховує не лише прямі сусіди, але й **глобальну структуру** графа.

**Складність:**
- Один шар: $O(|E| \cdot d)$ операцій (де $d$ — розмірність features)
- $L$ шарів: $O(L \cdot |E| \cdot d)$
- Для розрідженого графа (кожне місто з'єднане з $k \ll N$ сусідами): $|E| = O(kN)$, тому загальна складність $O(L \cdot k \cdot N \cdot d)$ — **лінійна** за кількістю вершин!

Порівняйте з Branch & Bound: $O(2^N)$.

## 3. AlphaFold 2: Біологічна аналогія як інженерне рішення

### 3.1. Парадокс Левінталя та енергетичний ландшафт

У 1969 році Сайрус Левінталь сформулював парадокс: білок з $N=100$ амінокислот має $\approx 3^{100}$ можливих конформацій (форм). Навіть якщо кожна конформація формується за $10^{-13}$ секунд, перебір усіх варіантів займе $10^{27}$ років — більше віку Всесвіту. Але білки згортаються за мілісекунди.

**Висновок:** Білки не перебирають конформації. Вони "відчувають" енергетичний ландшафт та спускаються до глобального мінімуму вільної енергії $E(\mathbf{r}_1, \dots, \mathbf{r}_N)$.

**Математична аналогія з VRP:**
- **Білок:** Мінімізація $E(\mathbf{r}_1, \dots, \mathbf{r}_N)$ за координатами амінокислот
- **VRP:** Мінімізація $C(\pi_1, \dots, \pi_K)$ за послідовностями відвідування (permutations)

Обидві задачі — це пошук глобального мінімуму на **високовимірному ландшафті** з експоненціальною кількістю локальних мінімумів.

### 3.2. Архітектура AlphaFold 2: Evoformer та Geometry Tower

**AlphaFold 2** (DeepMind, 2020) вирішив задачу згортання білків з точністю, що конкурує з експериментальними методами. Ключова ідея — розділення на два етапи:

1. **Evoformer:** Обробляє **еволюційну інформацію** (Multiple Sequence Alignment, MSA) та будує pairwise representation (матрицю взаємодій між парами амінокислот)
2. **Geometry Tower:** Перетворює pairwise representation у **3D координати** атомів

**Мапінг на VRP:**

| AlphaFold 2 | VRP / TSP |
|-------------|-----------|
| Амінокислота | Клієнт / місто |
| Поліпептидний ланцюг | Маршрут транспортного засобу |
| MSA (еволюційна історія) | Історія трафіку / паттерни доставки |
| Pairwise representation | Матриця відстаней / взаємодій |
| 3D структура | Оптимальна послідовність відвідування |
| Вільна енергія | Сумарна вартість маршруту |

**Чому це працює:**
Evoformer використовує **Attention mechanism** для виявлення довгострокових залежностей. Якщо дві амінокислоти часто зустрічаються разом у різних видах, вони, ймовірно, близько розташовані в 3D просторі. Аналогічно: якщо два клієнти часто доставляються разом (паттерн у даних), вони, ймовірно, мають бути в одному маршруті.

### 3.3. Invariant Point Attention (IPA): Геометрична інваріантність

**Проблема:** Класичний Attention (Transformer) не інваріантний до обертань. Якщо ми обертаємо координати, результат змінюється.

**Рішення AlphaFold 2: Invariant Point Attention**

Замість обробки координат напряму, IPA працює з **відносними позиціями** та **кутами**:

$$IPA(\mathbf{q}, \mathbf{k}, \mathbf{v}, \mathbf{T}) = \text{Softmax}\left(\frac{\mathbf{q}^T \mathbf{k}}{\sqrt{d_k}} + \text{GeomBias}(\mathbf{T})\right) \mathbf{v}$$

Де $\mathbf{T}$ — тензор трансформацій (обертання + переноси), а $\text{GeomBias}$ — функція, яка залежить лише від **відносних** позицій, а не абсолютних.

**Для логістики:**
Ми не хочемо, щоб модель залежала від конкретної системи координат (наприклад, чи використовуємо WGS84 чи UTM). IPA автоматично робить модель інваріантною до обертань та переносів.

## 4. Ізоморфізм задач: Доведення через редукцію

### 4.1. Формальне доведення NP-повноти

**Теорема:** Задача згортання білка (Protein Folding Problem, PFP) та Traveling Salesman Problem (TSP) є **NP-еквівалентними**.

**Доведення (напрямок TSP → PFP):**

Нехай маємо екземпляр TSP з $N$ містами та матрицею відстаней $D_{ij}$. Побудуємо білок:

1. Створюємо $N$ амінокислот, розташованих у лінійному ланцюгу
2. Встановлюємо енергію взаємодії між амінокислотами $i$ та $j$:
   $$E_{ij} = -D_{ij}$$
   (мінус, бо ми мінімізуємо енергію, а в TSP мінімізуємо відстань)

3. Додаємо обмеження: амінокислоти можуть згортатися лише так, щоб утворити цикл (замкнений маршрут)

4. Глобальний мінімум енергії $E = -\sum_{(i,j) \in \text{tour}} D_{ij}$ відповідає оптимальному маршруту TSP.

**Доведення (напрямок PFP → TSP):**

Нехай маємо білок з $N$ амінокислотами та енергетичною функцією $E(\mathbf{r}_1, \dots, \mathbf{r}_N)$. Побудуємо TSP:

1. Кожна амінокислота стає містом
2. Відстань між містами $i$ та $j$:
   $$D_{ij} = \min_{\mathbf{r}_1, \dots, \mathbf{r}_N} E(\mathbf{r}_1, \dots, \mathbf{r}_N) \text{ subject to } \|\mathbf{r}_i - \mathbf{r}_j\| = d_{target}$$

3. Оптимальний маршрут TSP відповідає послідовності згортання білка.

**Висновок:** Якщо AlphaFold 2 ефективно вирішує PFP, його архітектура може бути адаптована для TSP/VRP.

### 4.2. Чому геометричний підхід перемагає комбінаторний

**Комбінаторний підхід (Branch & Bound):**
- Перебирає **дискретні** стани (permutations)
- Кожен стан — це окремий вузол у дереві пошуку
- Складність: $O(2^N)$ вузлів

**Геометричний підхід (AlphaFold 2 / GDL):**
- Працює з **неперервним** простором (координати, embeddings)
- Градієнтний спуск знаходить локальний мінімум за $O(N^2)$ операцій
- Attention mechanism дозволяє "стрибати" через бар'єри локальних мінімумів

**Аналогія з фізикою:**
Комбінаторний підхід — це як перебір усіх можливих конфігурацій атомів у кристалі. Геометричний підхід — це як **молекулярна динаміка**: система сама знаходить енергетичний мінімум через неперервну еволюцію.

## 5. Інженерна реалізація: Пам'ять, паралелізм, throughput

### 5.1. Memory Layout для Graph Neural Networks

**Проблема:** Граф має змінну структуру. Як ефективно зберігати його для GPU?

**Рішення: Batching з padding або CSR format**

**Варіант A: Dense Batching (простий, але неефективний)**
```python
# Погано: для графа з N=10 та N=1000 вершин використовуємо однаковий розмір
batch_size = 32
max_nodes = 1000  # Найбільший граф у батчі
node_features = torch.zeros(batch_size, max_nodes, d)  # 32 × 1000 × 128 = 4.1 MB
adjacency = torch.zeros(batch_size, max_nodes, max_nodes)  # 32 × 1000 × 1000 = 128 MB
```
**Проблема:** 99% пам'яті витрачається на padding (нулі). Для графа з 10 вузлами ми виділяємо пам'ять для 1000.

**Варіант B: CSR Format (ефективний, але складніший)**
```python
# Добре: зберігаємо тільки реальні ребра
class GraphBatch:
    node_features: Tensor  # [total_nodes, d] - всі вузли всіх графів
    edge_index: Tensor     # [2, total_edges] - індекси ребер
    batch_ptr: Tensor      # [batch_size+1] - вказівники на початок кожного графа
```
**Переваги:**
- Пам'ять: $O(\sum_i |V_i| + \sum_i |E_i|)$ замість $O(\text{batch_size} \times \max_i |V_i|^2)$
- Для batch з графами розмірів [10, 50, 1000]: економія пам'яті $>90\%$

**Висновок:** Використовуємо **PyTorch Geometric** або **DGL** — вони автоматично конвертують графи в CSR format.

### 5.2. Паралелізм на GPU: Sparse Matrix Multiplication

**Операція Message Passing:**
$$H^{(l+1)} = \sigma(A H^{(l)} W^{(l)})$$

Де $A$ — матриця суміжності (sparse), $H^{(l)}$ — node features, $W^{(l)}$ — ваги шару.

**Складність на CPU:**
- Dense multiplication: $O(N^2 \cdot d)$
- Sparse (CSR): $O(|E| \cdot d)$

**На GPU (cuSPARSE):**
- Dense: $O(N^2 \cdot d / \text{cores})$ — обмежено bandwidth пам'яті
- Sparse: $O(|E| \cdot d / \text{cores})$ — ефективніше, бо читаємо тільки ненульові елементи

**Throughput для VRP з $N=200$:**
- CPU (Gurobi B&B): 1 instance за 60 секунд
- GPU (GDL model, batch_size=32): 32 instances за 0.1 секунди
- **Прискорення: $>19,000\times$**

### 5.3. Latency vs Throughput: Online vs Batch Inference

**Онлайн-режим (real-time):**
Клієнт робить замовлення → система генерує маршрут за $<1$ секунди.

**Архітектура:**
```
Request → GDL Model (single instance) → Route
Latency: ~50-100 ms (GPU inference)
```

**Batch-режим (офлайн оптимізація):**
Накопичуємо замовлення за день → оптимізуємо всі маршрути одночасно.

**Архітектура:**
```
Daily Orders → GDL Model (batch_size=1000) → All Routes
Throughput: 1000 routes за ~200 ms
Cost per route: 0.2 ms (в 500 разів дешевше)
```

**Висновок:** Для real-time використовуємо lightweight модель (менше шарів, менше параметрів). Для batch — повну модель з максимальною точністю.

## 6. Engineering Challenge: AI-Resistant Assessment

### 6.1. Задача: Проектування системи маршрутизації для 10,000 RPS

**Контекст:**
Ви будуєте систему доставки для мегаполісу. Пікове навантаження: 10,000 запитів на секунду (RPS). Кожен запит — це задача VRP з $N=50-200$ клієнтів.

**Вимоги:**
- Latency: $P_{99} < 500$ ms (99% запитів обробляються швидше 500 ms)
- Throughput: підтримати 10,000 RPS
- Точність: маршрути мають бути в межах 5% від оптимуму (відносно ручного розрахунку)

**Обмеження:**
- Бюджет: максимум 10 GPU (NVIDIA A100, 80 GB)
- Мережа: latency між серверами $<10$ ms
- Пам'ять: кожен GPU має 80 GB, але модель займає 20 GB

**Ваше завдання:**

1. **Виберіть архітектуру:**
   - A) Один великий сервер з 10 GPU (single node)
   - B) Розподілена система: 5 серверів по 2 GPU (multi-node)
   - C) Гібрид: 1 GPU для real-time (lightweight модель), 9 GPU для batch (повна модель)

2. **Обґрунтуйте вибір:**
   - Розрахуйте максимальний throughput для кожного варіанту
   - Оцініть latency (враховуючи network overhead для multi-node)
   - Порахуйте вартість (GPU-hours)

3. **Захистіть рішення:**
   - Чому ваш підхід кращий за альтернативи?
   - Які trade-offs ви прийняли?
   - Як система масштабується, якщо навантаження зросте до 50,000 RPS?

**Критерії оцінки:**
- **Недостатньо:** "Використаємо PyTorch та запустимо на GPU" (немає архітектурного мислення)
- **Добре:** Розрахунок throughput/latency з конкретними числами
- **Відмінно:** Аналіз trade-offs, масштабованість, обґрунтування через метрики (не інтуїцію)

### 6.2. Референсне рішення (для викладача)

**Рекомендована архітектура: C) Гібрид**

**Обґрунтування:**

**Real-time шлях (1 GPU):**
- Модель: 4 шари MPNN, $d=64$ (embedding dimension)
- Параметри: ~2M (займає 8 MB пам'яті)
- Throughput: 1000 instances/second на A100
- Latency: $P_{50}=30$ ms, $P_{99}=80$ ms

**Batch шлях (9 GPU):**
- Модель: 12 шарів MPNN + Attention, $d=256$
- Параметри: ~50M (займає 200 MB пам'яті)
- Batch size: 1000 instances per GPU
- Throughput: 9 × 100 instances/second = 900 instances/second
- Latency: 1-2 секунди (прийнятно для офлайн-оптимізації)

**Розподіл навантаження:**
- 90% запитів → real-time (1 GPU): 9,000 RPS
- 10% запитів → batch (9 GPU): 1,000 RPS → обробляється за 1.1 секунди

**Масштабування:**
Якщо навантаження зросте до 50,000 RPS:
- Додаємо 4 GPU для real-time (тепер 5 GPU, кожен обробляє 10,000 RPS)
- Batch залишається незмінним (10% = 5,000 RPS, обробляється за 5.5 секунд)

**Trade-offs:**
- ✅ Низька latency для більшості запитів
- ✅ Висока точність для складних випадків (batch)
- ❌ Складність: потрібна система черг (queue) для розподілу запитів
- ❌ Додатковий overhead: load balancer, monitoring
