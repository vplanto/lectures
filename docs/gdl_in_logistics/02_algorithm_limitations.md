## 1. Реальний тригер: Чому Google Maps не використовує точні алгоритми

### 1.1. Production Case: Затримка маршрутизації в Uber (2016)

У 2016 році Uber зіткнувся з проблемою: система маршрутизації для 10,000 водіїв у Нью-Йорку почала працювати повільніше. Замість 200-300 ms на генерацію маршруту, система витрачала 2-3 секунди під час пікового навантаження.

**Технічний розбір:**
- **Початковий підхід:** A* алгоритм для кожного водія окремо
- **Розмір задачі:** Граф доріг Нью-Йорка: ~300,000 перехресть (nodes), ~800,000 сегментів доріг (edges)
- **Навантаження:** 10,000 одночасних запитів
- **Проблема:** A* для кожного запиту перевіряє $O(b^d)$ вузлів, де $b$ — середня кількість сусідів (≈3), $d$ — глибина пошуку (≈50 для середнього маршруту)
- **Обчислення:** $3^{50} \approx 7 \times 10^{23}$ потенційних вузлів для перевірки (навіть з евристикою це мільйони)

**Рішення Uber:**
Замість точного A* для кожного запиту, вони перейшли на **precomputed shortest paths** (контрактні набори шляхів) та **machine learning** для передбачення оптимальних маршрутів. Це зменшило latency з 2-3 секунд до 50-100 ms.

**Висновок:** Точні алгоритми не масштабуються для real-time систем. Потрібні наближені методи.

## 2. Dijkstra Algorithm: Фундамент та фундаментальні обмеження

### 2.1. Математична формалізація

**Задача найкоротшого шляху (Shortest Path Problem):**
Дано орієнтований граф $G = (V, E)$ з вагами $w: E \to \mathbb{R}^+$ та джерелом $s \in V$. Знайти найкоротші шляхи від $s$ до всіх інших вершин.

**Алгоритм Дейкстри (1956):**
1. Ініціалізуємо відстані: $d[s] = 0$, $d[v] = \infty$ для $v \neq s$
2. Створюємо пріоритетну чергу $Q$ з усіма вершинами
3. Поки $Q$ не порожня:
   - Витягуємо вершину $u$ з мінімальною відстанню
   - Для кожного сусіда $v$ з ребром $(u,v)$:
     - Якщо $d[v] > d[u] + w(u,v)$, оновлюємо $d[v] = d[u] + w(u,v)$

**Коректність (доведення через інваріант):**
На кожній ітерації, якщо вершина $u$ витягнута з $Q$, то $d[u]$ — це найкоротша відстань від $s$ до $u$.

**Доведення (індукція):**
- **База:** $d[s] = 0$ — правильно
- **Крок:** Припустимо, що для всіх вершин, витягнутих раніше, відстані правильні. Нехай $u$ — наступна вершина з мінімальною $d[u]$. Якщо існує коротший шлях $s \to \dots \to v \to u$, де $v$ ще не витягнута, то $d[v] < d[u]$ (бо ваги невід'ємні), що суперечить тому, що $u$ має мінімальну відстань. Отже, $d[u]$ — оптимальна.

### 2.2. Складність та обчислювальні витрати

**Часова складність:**
- З бінарною купою (binary heap): $O((\lvert V \rvert + \lvert E \rvert) \log \lvert V \rvert)$
- З Fibonacci heap: $O(\lvert E \rvert + \lvert V \rvert \log \lvert V \rvert)$ — теоретично оптимально
- На практиці: бінарна купа достатня, Fibonacci heap має велику константу

**Пам'ять:**
- $O(\lvert V \rvert)$ для відстаней та попередників
- $O(\lvert V \rvert)$ для пріоритетної черги
- Загалом: $O(\lvert V \rvert)$

**Проблема масштабування:**
Для графа доріг України з $\lvert V \rvert = 500,000$ перехресть та $\lvert E \rvert = 1,500,000$ сегментів:
- Час: $O(2,000,000 \times \log(500,000)) \approx 2 \times 10^6 \times 19 \approx 38$ мільйонів операцій
- На CPU з 3 GHz: ~13 ms для одного запиту
- **Але:** Для 10,000 одночасних запитів це 130 секунд — неприйнятно для real-time

### 2.3. Чому Dijkstra не працює для VRP/TSP

**Проблема 1: Один шлях vs множина шляхів**
Dijkstra знаходить найкоротший шлях від $s$ до $t$. Але VRP потребує знайти **множину шляхів** (по одному для кожного транспортного засобу), які разом відвідують всі клієнти.

**Проблема 2: Обмеження**
VRP має обмеження:
- Вантажопідйомність: $\sum_{i \in \text{route}} q_i \le Q$
- Час роботи: $\sum_{(i,j) \in \text{route}} t_{ij} \le T_{max}$
- Часові вікна: $e_i \le \text{arrival}_i \le l_i$

Dijkstra не враховує ці обмеження. Навіть якщо ми модифікуємо алгоритм для врахування обмежень, складність стає експоненційною.

**Проблема 3: Комбінаторний вибух**
Якщо ми хочемо знайти оптимальний набір маршрутів для $K$ транспортних засобів та $N$ клієнтів, кількість можливих розподілів:
$$\text{Stirling numbers of the second kind: } S(N, K) = \frac{1}{K!} \sum_{j=0}^{K} (-1)^{K-j} \binom{K}{j} j^N$$

Для $N=50$, $K=5$: $S(50,5) \approx 10^{30}$ — неможливо перебрати.

## 3. A* Algorithm: Евристика як прискорення

### 3.1. Формалізація через оціночну функцію

**A* (1968) — узагальнення Dijkstra з евристикою:**
Замість мінімізації $d[u]$ (відстань від старту), мінімізуємо $f(u) = g(u) + h(u)$, де:
- $g(u)$ — реальна відстань від старту до $u$ (як у Dijkstra)
- $h(u)$ — **евристична оцінка** відстані від $u$ до цілі

**Умова допустимості (Admissibility):**
Евристика $h$ називається **допустимою** (admissible), якщо $h(u) \le d^*(u, \text{goal})$ для всіх $u$, де $d^*$ — справжня найкоротша відстань.

**Умова консистентності (Consistency):**
Евристика $h$ називається **консистентною** (consistent), якщо $h(u) \le w(u,v) + h(v)$ для всіх ребер $(u,v)$.

**Теорема:** Якщо $h$ допустима та консистентна, A* гарантовано знаходить оптимальний шлях.

**Доведення (напрямок):**
Якщо A* витягує вершину $u$ з $Q$, то $f(u) = g(u) + h(u)$ — мінімальна. Якщо $h$ допустима, то $f(u) \le g(u) + d^*(u, \text{goal}) = \text{оптимальна відстань}$. Отже, коли A* досягає цілі, вона має оптимальний шлях.

### 3.2. Вплив якості евристики на продуктивність

**Приклад: Евклідова відстань vs Манхеттенська відстань**

Для задачі пошуку шляху на сітці (grid):
- **Манхеттенська:** $h(u) = \lvert x_u - x_{goal} \rvert + \lvert y_u - y_{goal} \rvert$ (допустима, але слабка)
- **Евклідова:** $h(u) = \sqrt{(x_u - x_{goal})^2 + (y_u - y_{goal})^2}$ (допустима, сильніша)

**Експериментальні дані:**
Для сітки $100 \times 100$ з перешкодами:
- Dijkstra: перевіряє ~10,000 вузлів
- A* з Манхеттенською: ~3,000 вузлів (3× прискорення)
- A* з Евклідовою: ~500 вузлів (20× прискорення)

**Чому це працює:**
Сильніша евристика краще "направляє" пошук до цілі, уникаючи дослідження непотрібних напрямків.

### 3.3. Обмеження A* для VRP

**Проблема 1: Багато цілей**
VRP має множину цілей (всі клієнти). A* розроблений для однієї цілі. Можна запускати A* $N$ разів (від депо до кожного клієнта), але це $N \times O(|V| \log |V|)$ операцій.

**Проблема 2: Динамічні обмеження**
Після відвідування клієнта $i$, залишок вантажу зменшується: $Q_{remaining} = Q - q_i$. Це означає, що граф стає **динамічним** — ваги ребер залежать від стану. A* не підтримує динамічні ваги без модифікацій.

**Проблема 3: Часові вікна**
Якщо клієнт $j$ має часове вікно $[e_j, l_j]$, а ми прибуваємо в $t < e_j$, ми маємо чекати. Це означає, що "відстань" залежить не лише від простору, але й від часу. A* не враховує це безпосередньо.

**Модифікація: Time-Dependent A***
Можна розширити A* для часових вікон, але складність зростає з $O(|V| \log |V|)$ до $O(|V| \cdot T \log |V|)$, де $T$ — кількість часових слотів. Для $T=1000$ (секунди за день) це 1000× повільніше.

## 4. Branch & Bound: Точність за ціною експоненційної складності

### 4.1. Внутрішня механіка: Дерево пошуку

**Ідея:** Розбиваємо простір рішень на підмножини (гілки дерева) та оцінюємо нижню межу (Lower Bound) для кожної гілки. Якщо $LB \ge \text{поточний найкращий}$ (Upper Bound), гілка відсікається.

**Формалізація для TSP:**
1. **Розгалуження (Branching):** Обираємо ребро $(i,j)$ та створюємо дві гілки:
   - Гілка 1: $x_{ij} = 1$ (ребро включено)
   - Гілка 2: $x_{ij} = 0$ (ребро виключено)

2. **Обмеження (Bound):** Для кожної гілки обчислюємо нижню межу через релаксацію:
   - **1-Tree Lower Bound:** Видаляємо одну вершину, будуємо MST для решти, додаємо два найкоротші ребра до видаленої вершини
   - **Held-Karp Lower Bound:** Лінійна релаксація з subtour elimination

3. **Відсікання (Pruning):** Якщо $LB \ge UB$, гілка відсікається

### 4.2. Аналіз складності: Чому вмирає на $N > 20$

**Кількість гілок у найгіршому випадку:**
Для TSP з $n$ містами, дерево пошуку має глибину $O(n^2)$ (кожне ребро може бути розгалужене). У найгіршому випадку (коли відсікання не працює), кількість листків: $2^{n^2}$.

**На практиці:**
Ефективне відсікання зменшує це до $O(2^{cn})$, де $c \approx 0.1-0.3$ залежно від якості bounds. Для $n=20$: $2^{0.2 \times 20} = 2^4 = 16$ гілок (працює). Для $n=50$: $2^{0.2 \times 50} = 2^{10} = 1,024$ гілок (ще прийнятно). Для $n=100$: $2^{0.2 \times 100} = 2^{20} \approx 1$ мільйон гілок (повільно, але можливо). Для $n=200$: $2^{0.2 \times 200} = 2^{40} \approx 10^{12}$ гілок (непрактично).

**Пам'ять:**
Кожна гілка потребує зберігання стану (часткове рішення, bounds, constraints). Для $n=100$ це ~1 KB на гілку. Якщо одночасно активні $10^6$ гілок, це 1 GB RAM. Для $n=200$ з $10^{12}$ гілок це петабайти — неможливо.

**Експериментальні дані:**
- $n \le 15$: секунди на CPU
- $n = 20$: хвилини
- $n = 30$: години
- $n = 50$: дні-тижні
- $n = 100$: роки (навіть на кластері)

**Висновок:** Branch & Bound працює лише для малих задач ($n \le 50$). Для більших потрібні евристики або Deep Learning.

## 5. Прокляття розмірності (Curse of Dimensionality)

### 5.1. Математичне визначення

**Прокляття розмірності** — це явище, коли обчислювальна складність алгоритму експоненційно залежить від розмірності простору даних.

**Формалізація:**
Нехай $X \subseteq \mathbb{R}^d$ — простір даних розмірності $d$. Для рівномірного покриття гіперкуба $[0,1]^d$ точками з кроком $\epsilon$ на кожну вісь потрібно:
$$N(\epsilon, d) = \left(\frac{1}{\epsilon}\right)^d$$

Точок. Для $\epsilon = 0.1$ та $d=10$: $10^{10}$ точок. Для $d=100$: $10^{100}$ точок — більше атомів у Всесвіті.

### 5.2. Вплив на алгоритми оптимізації

**Приклад 1: Grid Search для гіперпараметрів**
Якщо ми маємо $d$ гіперпараметрів та хочемо перевірити $k$ значень кожного:
- Кількість комбінацій: $k^d$
- Для $d=5$, $k=10$: $10^5 = 100,000$ комбінацій (прийнятно)
- Для $d=20$, $k=10$: $10^{20}$ комбінацій (неможливо)

**Приклад 2: Nearest Neighbor для VRP**
Якщо ми зберігаємо базу даних з $N$ оптимальних маршрутів та хочемо знайти найближчий до нового запиту:
- Простір станів: $d = n + 5$ (координати $n$ міст + час + паливо + вантаж + історія)
- Для $n=50$: $d=55$
- Відстань між двома маршрутами потребує порівняння $O(n^2)$ пар міст
- Пошук найближчого сусіда: $O(N \cdot n^2)$
- Для $N=10^6$ та $n=50$: $10^6 \times 2,500 = 2.5 \times 10^9$ операцій — секунди на CPU

**Приклад 3: Monte Carlo для оцінки ймовірності**
Якщо ми хочемо оцінити ймовірність $P(X \in A)$ для випадкової величини $X \in \mathbb{R}^d$:
- Кількість зразків для точності $\epsilon$: $N = O(1/\epsilon^2)$ (незалежно від $d$)
- **Але:** Якщо $A$ має малу міру (volume), потрібно більше зразків для "потрапляння" в $A$
- Для $d=100$, якщо $A$ займає $10^{-10}$ об'єму гіперкуба, потрібно $10^{10}$ зразків для одного попадання

### 5.3. Чому точні методи вмирають на $N > 20$

**Комбінаторний вибух:**
Для TSP з $n$ містами кількість можливих маршрутів: $\frac{(n-1)!}{2}$.

| $n$ | Кількість маршрутів | Час перебору (1 операція/наносекунда) |
|-----|---------------------|----------------------------------------|
| 10 | $181,440$ | $0.18$ мс |
| 15 | $4.4 \times 10^{11}$ | $7$ хвилин |
| 20 | $6.1 \times 10^{16}$ | $2$ роки |
| 25 | $3.1 \times 10^{23}$ | $10$ мільйонів років |
| 30 | $4.4 \times 10^{30}$ | $10^{14}$ років (вік Всесвіту: $10^{10}$ років) |

**Експоненційне зростання пам'яті:**
Held-Karp потребує таблицю розміру $O(n \cdot 2^n)$:
- $n=20$: $20 \times 2^{20} = 20 \times 10^6 = 20$ MB (прийнятно)
- $n=30$: $30 \times 2^{30} = 30 \times 10^9 = 30$ GB (важко)
- $n=40$: $40 \times 2^{40} = 40 \times 10^{12} = 40$ TB (неможливо)

**Висновок:** Навіть з найкращими оптимізаціями, точні методи не можуть обробити задачі з $n > 50$ на сучасному обладнанні.

## 6. Локальні мінімуми: Чому евристики застрягають

### 6.1. Енергетичний ландшафт та басейни притягання

**Визначення:**
Для задачі оптимізації $\min_{x \in X} f(x)$, **енергетичний ландшафт** — це поверхня, де висота в точці $x$ дорівнює $f(x)$.

**Локальний мінімум:**
Точка $x^{*}$ називається локальним мінімумом, якщо існує окіл $U$ такий, що $f(x^{*}) \le f(x)$ для всіх $x \in U$.

**Басейн притягання:**
Множина точок, з яких градієнтний спуск (або локальний пошук) збігається до локального мінімуму $x^{*}$.

### 6.2. Аналіз для TSP: Кількість локальних мінімумів

**Теорема (випадковий TSP):**
Для випадкового розподілу $n$ міст на площині, очікувана кількість локальних мінімумів 2-Opt експоненційно залежить від $n$:
$$E[\text{# локальних мінімумів}] = O(2^{n/2})$$

**Доведення (напрямок):**
Локальний мінімум 2-Opt — це маршрут, для якого жодна заміна двох ребер не покращує вартість. Кількість таких маршрутів зростає експоненційно з $n$.

**Експериментальні дані:**
- $n=20$: ~$10^3$ локальних мінімумів
- $n=50$: ~$10^7$ локальних мінімумів
- $n=100$: ~$10^{15}$ локальних мінімумів

**Проблема:**
Якщо ми запускаємо 2-Opt з випадкової початкової точки, ймовірність потрапити в глобальний мінімум: $1 / \text{# локальних мінімумів}$. Для $n=100$ це $10^{-15}$ — практично нуль.

### 6.3. Методи виходу з локальних мінімумів

**1. Simulated Annealing (1983)**
Дозволяє приймати "гірші" рішення з ймовірністю, що зменшується з часом:
$$P(\text{прийняти гірше рішення}) = \exp\left(-\frac{\Delta E}{T}\right)$$

Де $\Delta E$ — збільшення вартості, $T$ — "температура" (зменшується з часом).

**Переваги:** Може "стрибати" через бар'єри між басейнами.
**Недоліки:** Потребує налаштування температури, повільна збіжність.

**2. Tabu Search (1986)**
Забороняє повертатися до недавно відвіданих рішень (tabu list).

**Переваги:** Швидше за Simulated Annealing для багатьох задач.
**Недоліки:** Потребує налаштування розміру tabu list.

**3. Genetic Algorithms (1975)**
Еволюційний пошук через мутації та схрещування популяції рішень.

**Переваги:** Може знаходити несподівані рішення.
**Недоліки:** Повільна збіжність, потребує налаштування параметрів.

**4. Deep Learning (наш підхід)**
Нейромережа навчається "бачити" структуру простору та передбачати оптимальні рішення без локального пошуку.

**Переваги:** Швидка інференція ($O(n^2)$), масштабується до мільйонів вузлів.
**Недоліки:** Потребує навчання, може мати помилку 1-5%.

## 7. Порівняльний аналіз: Точність vs Швидкість

### 7.1. Таблиця порівняння алгоритмів

| Алгоритм | Складність | Практична межа | Точність | Latency (n=100) | Масштабованість |
|----------|------------|----------------|----------|----------------|-----------------|
| **Brute Force** | $O(n!)$ | $n \le 10$ | 100% (оптимум) | Неможливо | ❌ |
| **Held-Karp** | $O(n^2 \cdot 2^n)$ | $n \le 30$ | 100% | Години | ❌ |
| **Branch & Bound** | $O(2^{cn})$ | $n \le 60$ | 100% | Хвилини-години | ❌ |
| **Dijkstra** | $O(|V| \log |V|)$ | $|V| \le 10^6$ | 100% (для SP) | Мілісекунди | ✅ (для SP) |
| **A*** | $O(|V| \log |V|)$ | $|V| \le 10^6$ | 100% (для SP) | Мілісекунди | ✅ (для SP) |
| **2-Opt** | $O(n^2 \cdot k)$ | $n \le 10^4$ | 95-98% | Секунди | ✅ |
| **3-Opt** | $O(n^3 \cdot k)$ | $n \le 10^3$ | 97-99% | Секунди | ⚠️ |
| **Lin-Kernighan** | $O(n^{2.2})$ | $n \le 10^5$ | 99-99.5% | Секунди | ✅ |
| **Simulated Annealing** | $O(n^2 \cdot \text{iterations})$ | $n \le 10^3$ | 98-99.5% | Хвилини | ⚠️ |
| **GDL/AlphaFold** | $O(n^2 \cdot L)$ | $n \le 10^6$ | 95-99% | Мілісекунди | ✅✅ |

Де $k$ — кількість ітерацій до збіжності, $L$ — кількість шарів нейромережі.

### 7.2. Вибір алгоритму за вимогами

**Сценарій 1: Офлайн оптимізація, мала задача ($n \le 30$)**
→ **Held-Karp** або **Branch & Bound**. Гарантований оптимум за хвилини.

**Сценарій 2: Real-time система, середня задача ($30 < n \le 100$)**
→ **Lin-Kernighan** або **GDL**. Точність 99% за секунди/мілісекунди.

**Сценарій 3: Real-time система, велика задача ($n > 100$)**
→ **GDL/AlphaFold**. Єдина опція для масштабування.

**Сценарій 4: Офлайн оптимізація, велика задача ($n > 100$)**
→ **Hybrid:** GDL для початкового рішення + 2-Opt/3-Opt для полірування. Краща точність за прийнятний час.

## 8. Engineering Challenge: AI-Resistant Assessment

### 8.1. Задача: Проектування системи маршрутизації для food delivery

**Контекст:**
Ви будуєте систему маршрутизації для food delivery сервісу (типу Glovo/Uber Eats). Система має обробляти 5,000 одночасних замовлень у мегаполісі.

**Вимоги:**
- **Latency:** Генерація маршруту для кур'єра: $<200$ ms (P99)
- **Точність:** Маршрути мають бути в межах 5% від оптимального рішення
- **Throughput:** 5,000 запитів/секунду пікового навантаження
- **Обмеження:**
  - Кожен кур'єр: максимум 5 замовлень одночасно (обмеження вантажопідйомності)
  - Час доставки: максимум 30 хвилин від замовлення
  - Температура: Гарячі страви мають бути доставлені за 15 хвилин

**Технічні обмеження:**
- Бюджет: 2 сервери (кожен: 16 CPU cores, 64 GB RAM, 1× NVIDIA V100 GPU)
- Граф доріг: 200,000 перехресть, 500,000 сегментів доріг
- Середня кількість точок на маршрут: $n = 3-8$ (3-8 замовлень на кур'єра)

**Ваше завдання:**

1. **Виберіть архітектуру алгоритму:**
   - A) A* для кожного запиту окремо (класичний підхід)
   - B) Precomputed shortest paths (контрактні набори) + жадібне призначення
   - C) GDL модель для генерації маршрутів + A* для уточнення
   - D) Hybrid: GDL для batch-оптимізації всіх замовлень + динамічне оновлення

2. **Обґрунтуйте вибір через метрики:**
   - Розрахуйте максимальний throughput для кожного варіанту
   - Оцініть latency (P50, P99) з урахуванням network overhead
   - Порахуйте вартість обробки одного замовлення
   - Оцініть точність (як порівняти з оптимальним рішенням для $n=8$?)

3. **Захистіть рішення:**
   - Чому ваш підхід кращий за альтернативи для цієї конкретної задачі?
   - Як система обробляє динамічні зміни (нові замовлення під час виконання маршруту)?
   - Які trade-offs ви прийняли (точність vs latency vs вартість)?

**Критерії оцінки:**
- **Недостатньо:** "Використаємо A*, бо він точний" (немає аналізу масштабування)
- **Добре:** Розрахунок throughput/latency з конкретними числами та обґрунтування
- **Відмінно:** Аналіз trade-offs, обробка динамічних змін, обґрунтування через метрики, врахування обмежень температури та часу доставки

### 8.2. Референсне рішення (для викладача)

**Рекомендована архітектура: D) Hybrid (GDL + динамічне оновлення)**

**Обґрунтування:**

**Етап 1: Precomputation (офлайн, раз на день)**
- Обчислюємо shortest paths між усіма парами перехресть через A*: $200,000^2$ пар
- Зберігаємо в форматі CSR: ~500 GB (прийнятно для 2 серверів)
- Час обчислення: ~10 годин на кластері (прийнятно для офлайн-задачі)

**Етап 2: Batch Optimization (кожні 30 секунд)**
- GDL модель обробляє всі активні замовлення (до 5,000) батчами по 64
- Throughput: 2 GPU × 64 instances/GPU × 10 batches/sec = 1,280 instances/sec
- Latency: $P_{50}=50$ ms, $P_{99}=100$ ms
- Точність: 3-5% від оптимуму (для $n=3-8$ це прийнятно)

**Етап 3: Динамічне оновлення (real-time)**
- Коли приходить нове замовлення, система швидко перепризначає його найближчому кур'єру через жадібний алгоритм
- Latency: $<10$ ms (простий пошук найближчого)
- Потім маршрут переоптимізується в наступному batch

**Загальна система:**
- **Throughput:** 1,280 instances/sec (обмежено GPU, але достатньо для 5,000/30 сек = 167 instances/sec)
- **Latency:** $P_{50}=60$ ms, $P_{99}=110$ ms (в межах вимог $<200$ ms)
- **Точність:** 3-5% від оптимуму (в межах вимог $<5\%$)
- **Вартість:** 2× V100 GPU + 32 CPU cores, енергоспоживання ~2 kW

**Порівняння з альтернативами:**

**A) A* для кожного запиту:**
- Latency: $P_{99} > 500$ ms (порушує вимоги)
- ❌ Не підходить для real-time

**B) Precomputed + жадібне:**
- Latency: $<10$ ms (відмінно)
- Точність: 10-15% (порушує вимоги $<5\%$)
- ❌ Недостатня точність

**C) GDL + A* уточнення:**
- Latency: $P_{99} > 300$ ms (A* уточнення занадто повільне)
- ❌ Не підходить для real-time

**Масштабування:**
Для 10,000 одночасних замовлень потрібно додати 1 сервер (тепер 3 сервери, 3× V100, 48 CPU cores). Система масштабується лінійно.
